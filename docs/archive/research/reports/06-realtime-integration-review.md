# Independent review of real-time voice integration

Review date: 2026-10-21. This review follows the user-selected direction: **the Space3044/chatgpt-web-voice upstream gateway, a pool of ChatGPT accounts, and native real-time voice**, with Cylo’s persistent control plane and Super handling business execution tools. It examines the boundary between the proposal and the source code; it does not claim that a running implementation is complete. No official API was called for this review, and official API fields are not treated as evidence of web-protocol capabilities.

**Selection is final. The checks in this review govern integration with Space and release of its capabilities; they do not decide whether to adopt or reject Space again.** [12](12-voice-super-boundary.md) supplements the authority boundary between the interactive Agent and Super: the voice Agent may reply autonomously in casual conversation, but it must not plan or execute business work in parallel with Super. A single execution entry does not prevent the voice Agent from making a false commitment, so response and playback control need separate work.

## 2. Minimum integration path and remaining boundaries

Use the selected gateway for account management and signaling. Cylo handles account leases, quota classification and cooldown, task events, and tool execution. Simple reads of real status use deterministic services; complex goals go to Super for a formal plan. The upstream’s spoken plan is only a proposal and must not automatically become a second execution plan. The browser handles audio and the DataChannel, and reports user turns to the authenticated Cylo backend; client events do not grant extra business permissions.

The smallest bridge worth studying is: **confirmed user turn → idempotent Cylo command → Super/tools → persisted result → ask the upstream to speak through the current client’s DataChannel using `relay_message`**. This is a new integration path; the existing source does not provide a complete loop. Without a stable completion signal, candidate transcripts may first be shown to the user for explicit submission. That supports “real-time voice + confirm to submit” only; it is not a hands-free automatic task loop. Silence timeouts and partial transcripts must not trigger business execution directly.

The upstream receives the microphone first and may reply on its own. A user prompt such as “Do not invent execution results” is not reliable control. Before claiming a business voice loop, verify response control or a trusted playback gate so that users do not hear a false “completed” report before execution finishes. Cylo records remain authoritative for result sources, task status, and failures. If text delivery is proven without controlling the first answer and checking result fidelity, only the real-time conversation channel is accepted; business result delivery is not. Automatically disabling the entire remote audio track would also damage natural conversation, so decide whether to implement it after testing latency and interruption behavior.

When changing accounts, close the old `PeerConnection`, release the old lease, and create a new `voice_session` and upstream thread. Keep Cylo’s task/command and local text context, then reconstruct the required summary in the new session using an input method that has been verified. Do not carry the old account’s conversation ID over as if it belonged to the new account. Verify summary injection and tool-result injection separately. Network reconnection must use idempotency keys to prevent replaying tasks.

## 3. Acceptance checklist

1. **Two-account quota experiment:** Separately simulate 401, 429, ordinary rate limiting, network errors, and actual voice-quota exhaustion. Keep redacted responses/events as evidence for classification, cooldown, and recovery. Do not permanently disable every 429 account or treat a generic 502 as known quota exhaustion. Account switching after exhaustion must show a reconnection notice, close the old media session, allow the new account to continue, and avoid rerunning the business task.
2. **Lease and stickiness:** Exercise two concurrent terminals, gateway restart, client disappearance, lease expiry, and redialing a released session. Check account capacity and owner isolation; prove that an expired lease is not rented again while the old media session may still be active. The current source does not provide this guarantee.
3. **Turn transaction:** Build fixtures from real redacted DataChannel events. Cover role distinction, duplicates, revisions, reordering, missing completion events, and a single sentence with a negative correction. Submit one command explicitly; do not treat assistant output or injected text as a new user command.
4. **Tools and spoken results:** Actually say “create task/check progress/cancel” and verify accurate reports for Super execution success, approval wait, failure, and unknown status. Do not report success if the tool did not run, the network is disconnected, or an injected result is repeated. Keep command/event IDs, real results, upstream messages, received transcripts, and recordings; testing text transmission alone is insufficient.
5. **Interruption and cancellation:** Verify muting, stopping playback, disconnecting voice, and canceling a business task separately. A user saying “stop for a moment” must not implicitly cancel a long-running task. Business cancellation must enter the authorized, idempotent cancellation flow; report external side effects that have already occurred truthfully.
6. **Mobile and recovery:** Test iPhone/iPad Safari, two-way talk using Mac speakers, lock-screen/background changes, microphone-permission changes, and multi-device takeover. Measure first-audio, interruption-stop, and account-switch reconnection delays. Record measured quantiles; do not infer performance from the name WebRTC.

# CAO + native Codex CLI continued transformation
Date: 2026-10-21. Scope: Official **Codex CLI**, official macOS desktop App not supported. Only design and source code verification are done here, and the product runtime is not submitted or the upstream implementation is modified. Voice continues to use Space3044 real-time upstream + gateway + multi-account pool, and the voice route will not be changed in this report.
## Direct conclusion
**Latest priorities: First-phase verification of automatic Super splitting, independent workers, multiple worktrees, long tasks, persistent recovery, product and cost. If you continue to use CAO, first change the Codex adapter, native session association, resume, stop viewing, and save results. Route A's manual thread attachment/handover control and complex handover protocols are reduced to optional follow-ups and are not used as selection or first-phase Go/No-Go front-ends. CAO is temporarily retained as a candidate for adoption, and further candidate comparisons are ongoing. ** There is no need to rewrite the Codex session engine for CLI connections, nor to replace CAO with app-server first.
The two operations should be separated:
- **CLI still running: Attach original tmux. ** CAO already has this capability. Users enter the same native Codex process, and the history, tools, and current interface are still there; no new CLI or thread ID is required to attach. The new key point is to suspend CAO automatic input and recycling to ensure that only people can write.
- **The original CLI has exited: the original thread is restored. ** Remember the official thread ID and host/store/worktree reliably before starting `codex resume <id>`. The current CAO Codex provider does not have this path, so the code needs to be supplemented. Restoring history alone does not equal restoring dead tool processes or unresolved approvals.
| Matching with requirements | Reuse and complement boundaries |
|---|---|
| Super/Worker, multiple CLI, collaboration, observable terminal | CAO is a matching orchestration base; reuses provider, MCP handoff/assign/send_message, inbox, existing database and workflow without redoing the entire schedule |
| Official CLI two-way connection | Supplement native identity, resume, manual control and security retention in CAO; the existing screen capture regularity, default `--yolo` and force cleanup are specific risks that need to be modified and are not enough to negate the entire project |
| Cylo complete product | Cylo outer layer supplements user business task/run, persistent client events, independent resident services, long-term memory and real-time voice/account pool; CAO workflow/terminal status does not automatically equal these product contracts |
The CAO terminal ID and tmux session/window name are both CAO/terminal identities, not Codex thread IDs. CAO's MCP `handoff` is the agent collaboration method, and it is not the human-machine control handover here.

### How to obtain thread ID reliably
1. **Prioritize accurate ID import. ** The user provides the ID from the native CLI, and CAO uses the official `thread/read` to verify it (no resume, no turn) and binds the same host/store/cwd. The official CLI `resume <UUID>` already exists; it cannot be automatically bound based on name or latest time only.
2. **CAO automatically discovers new CLIs. ** You can use the official app-server `thread/list` with the same CODEX_HOME to discover it, and then verify it with `thread/read`; the CLI source is `cli`, and you need to explicitly include `appServer` when discovering the app-server source. Use pre- and post-creation collections, independent worktree/cwd, time, etc. to filter, but these are not atomic launch correlations; if the candidate is not unique, the user must confirm it, and "latest" cannot be automatically selected. Only the same process attach is enabled before verifiable binding is obtained, and it is not declared that it can be resumed after exiting.
3. If the fixed CLI version provides the exact official session ID output, it can be captured first and verified with `thread/read`; the stable machine-readable launch-ID output of the interactive TUI has not been verified this time. The structured events of `codex exec --json` belong to another execution mode, and it cannot be claimed that the interactive CLI has the same interface.
4. Route A can only add a read-only discovery helper and use the app-server API, **without changing the turn execution to app-server**. This still has a protocol version dependency; if that dependency is not accepted, import with the user's explicit ID first. Reading native JSONL/SQLite can only be a compatible fallback that has been separately verified and fixed. The private table structure is not regarded as a stable API; the SQLite being written is not copied for "synchronization".
### Optional manual control process
- `beginManual`: Freeze CAO new distribution and re-roll → Wait for the current round/tool ​​to stop, or be explicitly selected by the user to interrupt → Confirm no in-transit input → Permanently grant manual → Attach the original pane. Only view can be parallelized, and only one party can enter.
- If you choose to start again `codex resume`: Exit the old CLI gracefully and confirm that it and related tools are no longer written, and then start the new official CLI. You cannot just detach the original pane and open a second writer. The same thread/store does not mean natural mutual exclusion across processes.
- `returnControl`: Same as pane detach when the original CLI can be kept alive; the second CLI mode must confirm that it is stopped. Resume distribution after checking identity, permission configuration, history and Git/file changes; externally added rounds are recorded as external execution and cannot be automatically regarded as Cylo tasks completed.
- Disconnection/lease expiration does not mean that manual CLI has exited; when CAO restarts, manual/unknown will be restored first and reconciled, and will not be automatically retrieved. The stop status of the shell subprocess, MCP server and background program are checked separately, and the disappearance of the tmux client cannot be used as proof.
**Permission Boundary:** A Retains CLI native tools and human TUI approval; no need to create separate mobile approval protocols during manual takeover. Unattended workers must remove the default `--yolo` and use an explicit profile/sandbox and controlled execution environment; the prompt constraint of CAO allowedTools is not an OS permission. Recovery must not silently re-inject higher privileges or a different supervisor prompt. CAO MCP tool credentials need to be bound to the owner/permission, and unauthorized distribution is prevented during manual operation; the native history does not carry the guarantee that "the tool service must still be online".
## Route B: Structured app-server adapter (select according to capabilities)
This is not adding a parameter to `_build_codex_command`. If Cylo must directly display tool events, remote approvals, `turn/steer`, and precise turn status, B is more suitable, but belongs to a deeper Codex integration.
- **B1 Add adapter in CAO: ** Abstract `BaseProvider`/Startup, input, status, output, termination boundaries in terminal service, Codex goes to app-server, other providers retain tmux; `ProviderManager` registers new implementation. The thread/turn/item ID is returned in a structured manner and is no longer inferred from the screen capture; the existing status/output API is used for compatible projection. `agent_step`, inbox, MCP `handoff/assign/send_message` retain Super/Worker collaboration semantics, but dispatch/completion/cancellation must map the real protocol; the terminal WebSocket is no longer directly equal to the native TUI of the runtime. For a deeper fork than A, the CAO upstream terminal needs to be maintained and assumed to be compatible with both ends of the Codex protocol.
- **B2 Cylo runtime adapter:** Cylo's `AgentRuntime` directly manages app-server, reusing CAO's Super/Worker role design or encapsulated collaboration entrance. CAO's original tools are mapped to the runtime through the gateway, and the entire terminal/workflow life cycle cannot be reused by just "changing commands". Only one scheduling and execution owner can be selected for the same run; CAO and Cylo cannot dispatch the same thread respectively. If CAO is still allowed to do the overall orchestration, it will be given an external runtime calling contract and will no longer pretend to be an existing tmux provider.
- Protocol mapping: create/resume/list/read → `thread/*`; send/steer/cancel → `turn/start`, `turn/steer`, `turn/interrupt`; completion and usage → turn/item notification; command/fileChange approval and user-input → server-initiated request/reply, press thread/turn/request/connection Associated with the decision version, expired request IDs cannot be reused.
- shell/file/MCP is executed by Codex itself. CAO collaboration tools are exposed via Codex's MCP configuration, or map experiments `dynamicTools` / `item/tool/call` after fixed version verification; the two are not naturally equivalent. The dynamic tool hosted by the client may not have a host that can respond when the independent CLI takes over. MCP services with consistent authentication and consistent access to CLI are preferred.
B still has to perform A's execution mutual exclusion, directory reservation, cancellation confirmation and recovery check; the manual handover state machine is only implemented when selected; app-server does not solve business tasks, budgets and side effect ledgers for Cylo. app-server is the name of the process protocol and **does not mean that this product supports official desktop apps**.
## What must be verified and what does not need to be done first for the CLI
Only CLI connection is done, there is no need to do desktop App discovery/deep link/project registration, App SSH handoff, cross-host relocation, moving one-by-one native approval bridge or complete app-server turn adapter. The default execution stays on the same host/store/worktree; remote terminals can SSH to that host to attach. The cross-environment data migration of the complete product is still retained and is subject to separate acceptance according to 04 Section 13/CY-04-03; what is canceled is the official desktop App support, not the data migration requirement.
The product still has to manage: business task/run status and real completion evidence, persistent execution owner/lease/fencing, process stop/unknown, dirty worktree and product, tool service credentials/permissions, backups, budgets, Cylo's own tool approval and external side effect checks. They cannot be presumed completed by "the CLI can resume".
Required acceptance for the first phase:
1. True CAO/tmux automatic Super splitting, independent Worker, multiple worktrees and long tasks; real progress/products/costs can be viewed, correct verification and execution after client exit and CAO restart, repeated inbox/re-investment will not cause double writing.
2. Basic Codex CLI call → save native thread/host/store/cwd → stop/exit or confirm that the old writer has stopped after crash → restore with the same ID. Catalog disappears with clear failure, uncommitted/untracked files remain, cannot be claimed recovered with just summary.
3. Real Codex shell/file/MCP and necessary approval/denial; after recovery, tools and permissions are configured correctly, interruptions, process exceptions and pending approval recycling are not repeated approval/execution, and old requests cannot be misused.
4. Cancel the child process that will continue to write by proving that stopping the round, exiting the CLI, and terminating the process respectively; if it cannot be proved, it will be unknown, the second writer will be rejected, and the false "stopped" cannot be returned.
Optional artificial enhancement and additional verification: manual takeover and handover of the same pane, automatic inbox/re-investment and manual input race conditions, read-only observation/disconnection/restart, CAO → official CLI → CAO same thread two-way new turn, and external thread import. Passing is only required when asserting the capability, failure to achieve does not block the first phase or the full required range.

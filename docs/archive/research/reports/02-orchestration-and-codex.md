## 1. Decision-making
**Current recommendation: CAO is temporarily reserved as a candidate for Super/Worker orchestration, and further candidate comparisons are still in progress; first verify automatic splitting, independent workers, multiple worktrees, long tasks, persistent recovery, products and costs, and supplement basic CLI execution/stop viewing/recovery; manual same-thread takeover is an optional follow-up. For specific source code changes and A/B routes, see [07 Transformation Plan](07-cao-cli-handoff-plan.md). ** Current scope is official CLI only; users are explicitly not required to have the official macOS desktop app. The following historical app documentation, entry points, and experimental restrictions are retained as out-of-scope evidence and are not product requirements, access, or delivery blocking conditions. Running the CLI and browser on macOS is not excluded.
This adjustment is based on the user's cancellation of the official desktop App scope and the fact that CAO already has real source code for tmux attachment, collaboration and persistence; it does not prove that all Cylo product requirements have been covered by CAO. Screen capture rules, default `--yolo`, and the risk of forced cleanup are still retained below as specific modification items.
CAO already has real tmux attachments for manual manipulation of the native CLI within the same run. In the first phase, the official thread ID binding and `resume` after CLI exit, stop viewing and result retention need to be supplemented; manual input/recycling mutual exclusion can only be supplemented when choosing to take over enhancements. CAO's own terminal/session ID cannot be used as the Codex thread ID. It is recommended that route A reuse its orchestration, the app-server adapter only adopt route B when structured tooling/approval/turn control is needed, and do not refactor the entire runtime for capabilities outside the scope of the desktop app.
**Already tested and limited:** "app-server first round → official interactive CLI same thread, new round → app-server third round" on Linux with the same host and CODEX_HOME, through the three rounds of text closed loop of isolating the fake provider; it does not mean that the CAO transformation has been completed, nor does it replace the real model, shell/MCP, approval and concurrent handover verification. App-server's own restart recovery has been tested; the same process tmux attaches and the same thread resumes after exiting, which are two types of takeover.

### 4.1 Accurate scope of transmission and authentication
Native `0.163.0` help explicitly supports `--listen stdio://` (default), `unix://` /path, `ws://`, `off`; CLI `resume --remote` supports `ws/wss/unix`. The official document is consistent, but it is clear **"The app-server command and WebSocket transport are experimental and aren't supported for production workloads."** The existence of Unix socket cannot be deduced into a complete set of app-server to obtain production support; the existence of remote CLI capability cannot prove that Mac App supports third-party remote servers.
Official Auth endpoints of `app-server.md` Original text:
> “If you’ve built a local or open-source application using Codex app-server authentication, you can continue using it…”
>
> “App-server authentication has never been permitted for commercial or hosted services. We launched Sign in with ChatGPT to support these use cases…”

**app-server authentication** is limited here. The open source license does not grant ChatGPT subscription resale/hosting authentication rights; nor can this sentence be expanded to "all commercial uses of Codex are prohibited" or "all API keys are prohibited". Local/personal Cylo can be designed according to the user's own supported local authentication method, but the recommended migration path and specific applicability of new applications should still be verified. Future commercial/hosted deployments should separately evaluate the official [Sign in with ChatGPT](https://developers.openai.com/siwc) (this article is only an official guide, and has not tested access/availability) or approved API/provider credentials, and do not reuse the user cache subscription token to serve as multi-tenant service authentication.
The certification document also clearly recommends API keys for programmatic Codex CLI/CI/CD; API billing, data retention, and feature availability are different from ChatGPT subscriptions. The entire user CODEX_HOME must not be shared with unrelated tenants. Certification itself does not migrate threads, files, or projects.

### 5.2 Optional native handover protocol (subsequent enhancement design, not yet implemented)
1. `requestHandoff(taskId, targetClient)`: Control the service to prevent new dispatch; save messages, task revision, threadId, turnId, hostId, CODEX_HOME logo, repo/worktree and dirty manifest. If it is still executing, wait for the terminal turn or request interrupt and receive confirmation; the database flag pause alone is not enough.
2. `sealHandoff`: Confirm that there are no active tools/approvals/unknown side effects; save the original history cursor and product. When there is pending approval, the original request and the validity period are bound; if the handover cannot be carried out safely, it will remain blocked and will not be automatically approved.
3. `openNative`: The CLI is attached to the original tmux when it is alive; it provides the precise official CLI resume command after exiting. Cylo/CAO stops automatic input and recycling during user operation.
4. `reconcileExternal`: Cylo re-list/read/paginate, read and update turn/items, Git and file changes, and native status; verify that the thread and worktree are still the same and then take back the write lease. New work added in the official tool is recorded as an external execution record; whether Cylo business tasks are completed still requires acceptance.
5. If it is found that the original thread is lost, the directory has been deleted, the tool is unavailable, or concurrent writing is found, enter `needs_reconciliation`; only clearly marked reconstruction options are provided, and no new threads are quietly created to pretend to be continued.
### 5.3 Historical capability classification (currently only CLI, B/C/E and App related descriptions are out-of-scope evidence)

The difficulty is not in copying the chat, but in figuring out who can write, how to keep the working directory, and how to check the results of unknown tools.

If optional enhancement A is selected, the complete operation should be:
1. The user clicks “Submit to Codex” on Cylo. Cylo stops dispatching new turns, waits for the current turn to end or interrupt to complete, and checks the background tools; it displays that the session has been suspended, the execution host and the working directory are displayed.
2. Control service archiving checkpoint: native thread/turn/history cursor, task acceptance target, permission configuration, Git HEAD/branch/dirty patch, untracked files and attachment references. Checkpoint is not a memory/process snapshot; there are unknown side effects that must be displayed for verification.

## 6. Integration interface and persistence boundary
`AgentRuntime` is the only session holder within Cylo (can be implemented by adapters on multiple execution hosts); Super proposes intentions and controls execution after service verification/persistence. Long services do not rely on Super sessions to survive.
| Interface | Input/Output | Required Semantics |
|---|---|---|
| `capabilities()` | runtime/version/schemaHash, discover/resume/steer/interrupt/approvals/nativeHandoff flags | Version-by-version and provider declaration; explicit downgrade if capability is missing |
| `discover(filter)` / `inspect(ref,cursor)` | hostId/storeId/threadId, source, cwd, status, turn/items paging | No side effects reading; no automatic resume of all found threads, no leakage of other items |
| `create(context, permissions, workspace)` / `resume(ref)` | Native thread/session/execution instance reference | create response is not equal to durable; only by verifying that the first input/history has been persisted can recovery be promised |
| `startTurn(runId,idempotencyKey,input)` | turnId + received/applied status | app-server is not assumed to provide business idempotence; persist the intent before sending, query first when the result is unknown, and prohibit blind replay |
| `steer(ref,expectedTurnId,input)` / `interrupt(ref,turnId)` | ack and final turn status | If the turn does not match, reject it; interrupt ack is not equal to side effect cancellation/all child processes stop |
| `respondApproval(binding,decision)` | native request + Cylo decision revision | Permission verification, validity, deduplication, native resolved evidence; expired requests cannot be approved |
| `events(cursor)` / `reconcile(ref)` | raw eventRef, normalized event, usage and integrity flag | Cylo independent durable event/outbox number; native stream disconnection is not considered to be resumable without loss |
| `handoff` / `reclaim` / `retainWorkspace` | Ownership status and product retention records | Do not duplicate it with another adapter, do not automatically destroy the worktree as a temporary directory |
It is recommended to record `taskId/runId/attemptId ↔ hostId/runtimeVersion/storeId/threadId/sessionId/turnId/worktreeId` permanently and save the write lease epoch, commit/patch/untracked product, approval binding, native history cursor, observed tool results, budget estimate and bill usage source. Cylo tasks/permissions/confirmed decisions are authoritative; Codex thread history is a native execution record; memory summary is only traceable derived material. Token statistics may be delayed, and the usage notification cannot be used as a precise hard limit; when the budget is reached, new distribution must be stopped and processing is already in progress.

| Double writing of native tools or another process is still running | Overwriting code, repeated operations | Handover with daemon or provable execution end lock/exclusive; Refuse to write after concurrency is discovered; No-Go automatic takeover if coordination is not possible |
| thread/start has not been downloaded | The reception is successful but cannot be restored | The create mark is being initialized; the first input is persistence confirmation; it can be restored by pressing the map after killing the process; it cannot be marked as "saved" without evidence |
| WS/command experiment status and version drift | Compatible with interruptions, no production support | Fixed release version + schema, start/resume/steer/interrupt/approval/pagination regression passed, clearly accepting support risks; if reliability requirements are not met, No-Go production dependence |
| Subscription authentication is used for hosting business | Does not comply with the official app-server authentication scope | Local mode is isolated from hosted product authentication; hosting is completed and applicable SIWC/API solution availability and terms verification, otherwise No-Go shared subscription token route |
| CAO default yolo and prompt constraints | Unauthorized writing/network/external operations | Prohibit default unrestricted paths, actual sandboxes/containers and permission audit tests; if operation permissions and approval closed loop cannot be performed, No-Go main path |
| CAO worktree automatic force cleanup | Loss of results | Explicit cleanup only after stopping operation and confirmation of product retention; do not let CAO own the Cylo key worktree life cycle before modification |
| Broken flow/repeated callbacks | False completion, repeated external side effects | Durable inbox/outbox, native turn/result verification, unknown results entering the manual/compensation path; insufficient natural language completion |

| Migrate workspace or store across hosts | File, path, WAL, credential mismatch | Prioritize connection and execution host; relocation must stop writing, consistent backup, file and environment verification; hot copy and synchronization are not supported |
| Token/running budget delay | Excess cost/idle | Control service hard limits on new dispatch, concurrency and tool budget; record cache/input/output/retry/Super overhead, cannot rely solely on model awareness |

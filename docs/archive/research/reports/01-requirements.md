# Cylo new version of requirements tracking, acceptance and delivery boundaries
Survey date: 2026-10-21. Read this article in full and use [new version of complete requirements](../product-requirements.md) as the only product requirements baseline; [old requirements and architecture discussion draft](../codex-super-agent-requirements-and-architecture.md) only for historical comparison. The current baseline has canceled official Codex desktop App support according to the latest user decision; the basic CLI, macOS client/browser and cross-environment migration are retained. The server platform is subject to the latest scope description below, and the §5.2 number is retained. The latest priority also changes manual and thread seamless takeover, two-way native handover and complex control protocols to optional enhancements; basic CLI execution, stop viewing and persistent recovery are still required. The following components, stages, data structures and numerical indicators are implementation suggestions, not a rewrite of the original text, nor capabilities that have been implemented or measured.
**The latest platform scope (takes precedence over the old dual-platform expression in the table below):** In the first phase, only Linux server and execution host deployment and basic CLI execution, stop viewing and recovery are guaranteed; in the table, Mac/Linux background, dual-platform CLI and Mac→Linux execution recovery acceptance, the first phase is based on Linux host operation/migration acceptance. macOS client/browser, user-used CLI, cross-device project access and backup export are retained; subsequent on-demand evaluation of Cylo/AO/Worker background services running on macOS will not be included in the first phase of acceptance. Stable requirement ID reserved.
## 1. Conclusion and evidence boundaries
Cylo is a persistent, open execution system. The client, task authority state, Agent, long-term service and long-term memory must be separated; it cannot be reduced to a chat interface or terminal Agent orchestration. The required scope of all 22 chapters jointly defines the final product. Scenarios A-E are cross-component acceptance links; the delivery of a subset of any stage does not represent the completion of the final product.
Chapter 5 needs to distinguish between basic CLI execution/stop viewing/save session recovery, and optional manual session discovery, reverse identification, and running input handover. Failure in basic recovery will block the corresponding automatic execution of the closed loop; the lack of manual seamless handover will no longer block model selection or required range acceptance. Regardless of whether enhancements are implemented, uncoordinated double-writing must be prevented and support boundaries must be faithfully marked; exporting summaries or rebuilding chats must not pretend to be native session recovery.
This article is only based on the analysis of two requirement documents from the warehouse and does not independently claim that the candidate project supports a certain capability. External facts about candidate code, official protocols, and speech platforms are provided by the same directory orchestration/speech/architectural research respectively; this article lists the evidence that needs to be obtained. Warehouse static reading, interface document description and real end-to-end pass must be recorded separately.

## 3. Matrix reading and responsibility boundaries
The stable ID format is `CY-Chapter-Item`, which corresponds to the original section first; chapters without sections are split into clear entries. The ID does not change with future implementations, file line numbers, or stages. Scenes use `CY-19-A` to `CY-19-E`. Each row contains original provenance, requirements, responsible components, dependencies/risks, earliest delivery stage, and verifiable acceptance; comma-separated bullet points are covered by that row.
Components: **Client**=macOS/iPhone/iPad interactive client; **Control Plane**=request/project/task/event/authoritative-state control plane; **Adapter**=Codex and other Agent/model adapters; **Orchestration**=Super/Worker planning and execution; **Service**=ordinary program/service registration and lifecycle management; **Memory**=history, sources, memory organization and retrieval; **Security**=identity/authorization/isolation/audit; **Operations**=runtime supervision, health, recovery, backup and deployment. The listed component has primary responsibility; this does not exclude other components.
Stage: **P0** = blocking POC and protocol/state contract; **P1** = trusted tasks and cross-device development closed loop; **P2** = long-term service, independent expansion and reliable memory closed loop; **P3** = complete cross-platform/replacement/migration/quality acceptance. The stage is the goal of delivering the complete article at the earliest; POC starts at P0, even if the function is delivered later. **Direct**=can be implemented directly according to the mature engineering method, but acceptance is still required; **Trial**=must have POC first and cannot just rely on the plan commitment. A POC is not proof of production readiness.

# Super/Worker open source alternative: source code verification and technology stack selection
Abbreviations: **CAO = awslabs/cli-agent-orchestrator (Python)**; **AO = OrchestratorInc/agent-orchestrator (Go)**. The two are different projects.
Date: 2026-10-21. Scope: Up to five alternative projects + CAO baseline; read-only networking and fixed HEAD static verification, not deployed, not using real accounts, not submitting runtime.
## Current priorities and conclusions
Latest user adjustments: **Automatic Super decomposition, independent Worker, multi-tasking/worktree, persistent recovery, background service, expansion cost priority; manual seamless takeover is an optional enhancement. ** macOS/Linux CLI execution, viewing progress, stopping, and session resumability remain. The official Codex desktop app is out of scope. The same technology stack is an important preference, and the real-time voice upstream and external account pool cannot be discarded because of this.
**There are better candidates than CAO in specific aspects: AO is the most complete orchestration base worth comparing for replacement; OpenClaw is a strong candidate for the TypeScript serving/extension route. **Both have real auto-derived workers, persistent state and worktree and cannot be excluded by "multi-terminal UI" or "chatbot". The existing CAO + CLI enhancement route is still executable; the static evidence at this time is not sufficient to directly declare that it should be completely replaced.
- **Go Main Line Priority Comparison AO + Space3044 Voice Gateway. ** AO's Go daemon is more consistent with the Space Go service in terms of back-end language. Native Codex ID/recovery, independent host, and product interface are ready; Cylo still needs to complete business tasks, budget/products, service hosting, and permission restrictions. Not one Go binary can merge the two products.
- **Python mainline retains CAO. ** Existing FastAPI/MCP/SQLite/workflow and research assets are suitable for Python voice processing (such as Pipecat), or for Go voice gateway to run independently; see [07](07-cao-cli-handoff-plan.md) for the transformation path. After manual seamless takeover downgrade, it is not necessary to put in the complete handover state machine first.
- **TypeScript mainline evaluates OpenClaw first. ** True subagent/ACP, Codex app-server plug-in, managed worktree, background installation and expansion interface are more complete than building the client yourself; the price is to accept its Gateway/session/plugin system and larger upgrade area. The language can be the same as the Node voice worker, and the Space Go upstream/account pool can still be accessed independently through the interface.
Shortlist selected by criteria, not sorted by stars or made-up scores: **AO (Go product base), CAO (Python minimal overhaul), OpenClaw (TS extension/resident service)**. VK is an alternative for the development workbench; Happy/Hapi is preferred as a reference for client capabilities.

## AO: The strongest direct replacement candidate, especially suitable for Go mainline
It has been verified that it is not just a multi-terminal panel: `orchestratorSystemPrompt` specifies that the coordinator only coordinates, use `ao spawn/send` to delegate independent workers, and route CI/review; it does not rely on the built-in subagent to mix in the same process. `Manager` provides create/restore/reconcile, the workspace adapter allocates Git worktree, and the daemon API can be encapsulated by Cylo.
The advantage of native Codex is that it has already implemented many features in the 07 plan: hook reports AgentSessionID, `GetRestoreCommand` generates `codex resume`; Chat uses app-server and can bridge the same native UUID. The persistent state machines of the interface include claim, drain/interrupt, pending decision fail-closed, and restart recovery. **This part is indeed more mature than the current CAO, but seamless takeover is no longer a decisive condition for the first phase. **
Independent host and startup recovery are also closer to the requirements of long-term tasks: new sessions give priority to persistent PTY host, failure fallback tmux; Chat has detached host; SQLite retains controller generation and transition. The resident daemon is not an ordinary arbitrary service manager. Cylo's long-term HTTP service/build watcher still requires a separate ServiceRun contract.
Restrictions that must be retained:
- `restoreArgv` FreshLaunch can replay the saved prompt when the native session does not exist. Saving the workspace does not mean preserving the same thread. Cylo must recognize RestoreMode and prohibit silent counting of new sessions as continuation of the original run; lost external write operations cannot be automatically redone.
- In `CodexPermissionArgs`, accept-edits/auto goes on-request, and the **default branch returns `--dangerously-bypass-approvals-and-sandbox` **. The default cannot be used as a security configuration; permissions must be explicitly selected and execution isolation must be added, and repairs must not be skipped just because the project has an approval UI.
- `ao daemon` can be run independently; the self-hosted setup document provides Ubuntu user services, but the remote-host process is labeled experimental, and the official client remote discovery/pairing is coupled with AO account/cloud. Cylo prioritizes local API/controlled deployment and does not directly copy its accounts and tunnels.
- The root license Apache-2.0 and some packages MIT need to be processed according to the reuse scope; desktop, mobile, cloud, review and other large products are upgrade costs, not free and tailorable commitments.

## OpenClaw: Strong candidate for TS resident control plane, not excluded due to optional takeover
`sessions_spawn` actually provides subagent/acp two types of runtime, isolated/fork context, visible session, worktree parameters and asynchronous result delivery. The subagent registry has generation/owner verification, persistent writing and interruption recovery, and the managed worktree has allocation lease, owner protection and lossless GC; it is not just a chat channel or a pan-API agent loop.
Codex extensions include app-server harness, native thread catalog, persistent binding/lease and `thread/resume`; this HEAD managed version pin is 0.162.1 and is externally compatible with floor0.149.0. **You cannot follow the old impression that OpenClaw does not retain Codex native sessions. ** The supervision, snapshot fork and ordinary resume are different paths, and must still be accepted by the path chosen by Cylo.
Compared with CAO: dynamic TS plug-in/SDK, resident Gateway, service installation, multi-channel and sandbox/managed worktree system are more suitable for expansion into a generalized assistant; if Cylo is TS-oriented and requires resident automatic tasks rather than just a coding workbench, it may be more suitable. The price is wider configuration/plugin/state database boundaries; the logical subagent or worker thread does not automatically equal the independent supervised OS Worker required by Cylo, and the Codex/ACP independent execution path needs to be selected and verified.

## Vibe Kanban: There are orchestration tools, but isolation and recovery semantics need to be reexamined
Currently, there is indeed `orchestrator_mode_router`, which limits the workspace context and exposes create/list/update session, run_session_prompt, and execution status; it is explicitly prohibited to run the coding agent in the orchestrator's own session. So you can't say "multi-terminal UI only".
However, the tool `create_session` creates a session in an existing workspace; scoped orchestrator cannot list/delete workspaces arbitrarily, and **different Worker sessions do not automatically obtain different worktrees**. The tool scope/distribution strategy needs to be changed to meet the isolation of each worker. Codex `launch_codex_agent(resume_session)` actually calls `thread_fork`, not `thread_resume`; new threads generated in historical connections cannot be restored by pretending to have the same ID, and it must be marked even if manual seamless takeover is optional.
Its dashboard, code differences, review, and workspace/API are more suitable for interactive product development; Codex's default workspace-write/on-request has clear security configurations. Database persistence does not prove that active processes continue after a server crash. This point was not tested this time.

## Other findings and candidate boundaries
OpenHands/OpenHands warehouse API confirms the existence, MIT, and recent maintenance; this round is to control the depth ratio, there is no clone or similar capability conclusion, and it cannot be claimed that the native Codex CLI connection is missing/available based on this. If you pay more attention to the container development environment and API agent runtime in the future, you can select them separately; this round does not occupy the direct replacement recommendation position.
API control frameworks such as LangGraph/AutoGen can complement persistent business processes if used as Super; unless there is a native CLI adapter and retain the ID/working directory/permission/status protocol, it is just a **control layer reinforcement** and cannot be directly equivalent to the CAO/AO native CLI fleet. Manual takeover downgrades allow them to be considered, but do not exempt independent workers from recovery acceptance.
## Whether it should be replaced, and the minimum acceptance threshold
** "Discover Larger Items" is now not completed as a replacement. ** If you insist on Go in the first phase and hope to reuse existing product capabilities, AO will enter the first comparison position, and the evidence is enough to change the candidate scope of "only check CAO"; if you want minimal changes and the Python team takes the lead, CAO is still reasonable. If the team prefers TS, generalized background assistants and plug-in extensions, OpenClaw is more worthy of investment than Happy/Hapi.
| Decision conditions | Proposal and what to lose |
|---|---|
| Go control surface + Space Go voice service | Prioritize AO and compare PoC; get ready-made native/host/UI, lose CAO Python lightweight adaptation and be directly compatible with existing MCP/workflow |
| Python control surface / minimal transformation in the first phase | Keep CAO; get the minimum migration cost, still need to add CodexID/resume, security cleanup, permissions, task outbox; seamless handover can be post-installed |
| TS control surface + multi-channel/automatic task | OpenClaw compares with PoC; gets plug-in/backend system, loses CAO simple tmux/provider model, needs to accept Gateway/session and version upgrade surface |
| Just move the portal better | Happy/Hapi is used as a client reference, do not introduce a second supervisor to control the same Worker at the same time; it will increase the relay/hub boundary |
The three main lines will be jointly accepted, and there will be no additional first-phase veto items for manual seamless takeover:
1. **True Supervision Closed Loop**: One Super splits two tasks, and two independent Workers/OS execute owners and different worktrees. They can report asynchronously and reassign failure; the final acceptance is based on products/tests instead of screen idle or message delivery.
2. **Long term and recovery**: Close the UI, restart the controller, kill the Worker, restart the host, and check the four layers of task/native thread/process/side effects respectively; pending approval and external write unknown cannot be blindly replayed. Business tasks/run, budget, artifact/outbox still belong to Cylo.
3. **Session Continuity**: Capture the real native ID and put it on the disk; explicitly resume to restore the existing history after stopping; fresh/fork must be marked separately and must not be successful as the same thread. It only requires the ability to stop/view/continue, without the need for seamless takeover in the first period.
4. **Permissions and Products**: Remove dangerous defaults, verify shell/file/MCP approval rejection and configuration inheritance; cancel confirmation of child process stop; preserve dirty/untracked worktree before GC. Git worktree is file isolation, not a security sandbox.
5. **Ordinary service and voice decoupling**: Permanent construction/HTTP service independent supervision/log/stop, Worker exit will not accidentally kill or leave behind writers; the voice gateway account pool is accessed through the authenticated idempotent command/event API, and the audio does not enter the supervision model cycle.
6. **Actual cost of the same stack**: Select a backend main line and first make an end-to-end semantic command→Task→Worker event→Voice response; count the adapter/status/API faces that need to be forked. AO's Go, CAO's Python, and OpenClaw's TS cannot be regarded as the same stack just because the interfaces are all TS.

## 2. Minimum access solution and the boundaries that must be filled
A designated gateway is used to maintain accounts and signaling; Cylo is responsible for account leasing, quota classification and cooling, task events and tool execution; simple real status query provides deterministic services, and complex goals are handed over to Super to form a formal plan. The upstream verbal plan can only be used as a proposal and will not automatically be converted into a second execution plan. The browser assumes audio/DC and reports user turns to the authenticated Cylo backend; client events do not grant additional business permissions.
The smallest bridge that can be studied is: **Explicitly completed user round → Cylo idempotent command → Super/Tools → Dropped results → Request upstream broadcast via current client DC `relay_message`**. This is a new project route, and the ready-made source code does not have a complete closed loop. When there is no stable completion signal, candidate subtitles can be displayed first and submitted explicitly by the user; at this time, only "real-time voice + confirmation submission" can be accepted, and it cannot be called a closed-loop hands-free automatic task. Silent timeout or each partial cannot be used to directly trigger business execution.
If the upstream receives the microphone first, it may generate an autonomous reply first; writing a user prompt of "Don't make up execution results" does not mean reliable control. The formal business closed loop must verify response control or trusted playback gate control to ensure that false reports of "completed" are not played to users when the execution is not completed; the source of results, task status, and failure are all based on Cylo records. If you only prove that the text can be delivered without controlling the first answer and result fidelity, you can only accept the real-time dialogue channel and cannot declare that the business broadcast is completed. Automatically turning off the entire remote audio track will destroy the natural real-time conversation experience, so the decision to implement it needs to be made after testing the latency and interruption experience.
When changing accounts: close the old PeerConnection, release the old lease, create a new voice_session and upstream thread; retain Cylo's task/command and local text context, and use the verified input method to reconstruct the required summary in the new session. You cannot bring the old account conversation ID to pretend to be a new account to continue the conversation; any digest injection and tool back-injection must be verified separately. Network reconnection must also press the idempotent key to prevent task replay.
## 3. Acceptance Checklist
1. **Two account quota experiments**: Simulate 401, 429, ordinary current limit, network error and real voice quota exhaustion respectively, retain desensitization responses/events to prove classification, cooling and recovery; all 429 cannot be permanently disabled, nor can general 502 be regarded as a known quota exhaustion. There will be a visible reconnection prompt when switching out, old media will be closed, new accounts can be continued, and business tasks will not be redone.
2. **Lease and stickiness**: Two terminals are concurrent, the gateway is restarted, the client disappears, the lease expires, and the released session is dialed again; check the account capacity and owner isolation to prove that the expired lease will not be rented repeatedly while the old media is still active. The source code itself does not have this guarantee.
3. **Round transaction**: Create fixtures from real desensitized DC events, covering role distinction, duplication, revision, disorder, no completion event, and the same sentence containing negative corrections; only submit a command explicitly, and do not use the assistant or the back-note text as a user command again.
4. **Tools and Reporting**: Actually say "Create Task/Check Progress/Cancel" to verify that Super's successful execution, waiting for approval, failure and unknown status are reported accurately respectively; success shall not be reported when the tool is not running, the network is disconnected, or the result is repeated. The evidence includes command/event ID, real results, uplink messages, received subtitles and recordings. You cannot only verify the text sending function.
5. **Interruption and Cancellation**: Mute, stop broadcasting, disconnect voice, and cancel a business task are verified separately; the user says "stop" will not implicitly cancel the long-term task. It is clear that business cancellation must enter the authorization and idempotent cancellation state, and external side effects that have occurred must be reported truthfully.
6. **Mobile and Recovery**: iPhone/iPad Safari, Mac speaker dual-talk, screen lock/background switching, microphone permission changes and multi-device preemption; test the first voice outage, interruption stop and number change reconnection delay. Performance targets must be recorded as measured quantiles and cannot be inferred from the WebRTC protocol name.

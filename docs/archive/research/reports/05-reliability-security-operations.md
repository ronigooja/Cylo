## 2. Life cycle: control intentions, process facts and products are saved separately
**design. ** Do not use one `running` field to express task goal, process survival and service health at the same time. Use the 04 entity and complete the following transfer conditions:
| Object | Persistent state and advancement basis | Stop/resume/clean up boundaries |
|---|---|---|
| Task / TaskRun | task saves the target/acceptance; run saves attempt, runtime/host, native execution ID, resource epoch, checkpoint and observation time. Acceptance is carried out after the run output is completed | Pause/cancel is recorded first, and the process/tool ​​is observed to converge after stopping; the interrupted modifications and effects are still retained. Resume creating a new attempt and associate the original session without automatically rerunning completed steps |
| CapabilityRelease | source revision, lockfile, build environment, artifact digest, manifest, test and approval summary are immutable | There is no production secret and no deployment permission in the build phase; published files cannot be overwritten in place; used digests cannot be GC |
| Deployment | release+config version+grant+host generation constitutes the expected deployment; save rollout phase, old version, migration and rollback statement | Command replay of the same deployment cannot install a second copy; use expected_version for concurrent updates; rights expansion/target change and re-authorization |
| ServiceInstance | supervisor identity, process startup identity, generation, observed, health, last heartbeat; every time the service is triggered, record invocation/job | stop must cover the child process; pause by default, stop new triggers, and process according to the drain/cancel policy in transit; the exit of the control process is not equal to the service exit |
| Trigger / Schedule | Unique event native ID/logical time slot, timezone, misfire policy, cursor and last successful checkpoint | Disable trigger and delete ability separately; expired trigger according to skip/latest/bounded catch-up; prohibit unlimited reissue after recovery |
A capability release should leave a replayable **control record** instead of replaying an unconstrained installation shell: Prepare → Verify artifact/config → Check approval and resource budget → Freeze new trigger → Process in transit → Save checkpoint/old configuration → Install new instance → Probe verification → Switch generation → Registration successful → Delay recycling of the old version. In the failed save phase, it cannot just display "Deployment failed, please try again".
The checkpoint needs to be marked with schema, producer release, resource scope, external cursor and checksum; the cursor advances the same transaction as the generated job to prevent "recorded as read but not processed". Dual-version parallelism is only enabled when the consumption partition is separated, the provider supports consumer groups, or the resource side rejects the old generation. Single-active mail monitoring, file modification, and database migration are stopped and restarted by default; simply "two processes get different worktrees" cannot protect shared mailboxes or third-party APIs.
**Rollback design. ** The fact that release can be rolled back does not mean that the state can be rolled back. Use expand/contract database migration; if the old version of the new checkpoint cannot be read, the rollback must use verified conversion or roll forward repair, and the old checkpoint cannot be overwritten on the external resources that have been advanced. Database recovery, sent notifications/emails, and submitted orders are not undone by binary rollback. Uninstallation first stops the trigger/process tree, revokes grants and credentials, seals the results, and finally deletes the installation according to the retention policy; data erasure and uninstallation are authorized separately, and the minimum necessary metadata is retained for auditing.
**fact. ** Linux systemd `KillMode=control-group` will process the entire unit control group when stopped; `process` only terminates the main process, `none` does not provide this stop guarantee [R10]. This is a usable execution basis and does not prove that the actual unit has been configured correctly. If macOS background operation is supported in the future, launchd installation, user exit/restart behavior and child process termination require real machine acceptance; Linux configuration names cannot be directly transplanted to Mac.
## 3. Durable queue: Selection of SQLite, PostgreSQL jobs and Temporal
| Plan | Applicable conditions (design) | Official boundaries and work that cannot be omitted |
|---|---|---|
| SQLite WAL jobs in the same database | A single control host, a local reliable disk, a business write port, and can accept a single writer; test the queue lag and write lock wait first | WAL requires shared memory with the host and one writer at the same time [R2]; not a multi-node shared disk queue. FULL, short transactions, busy policy, checkpoint and disk water level still need to be configured |
| PostgreSQL jobs | Multiple control processes/nodes, high-availability databases or team write concurrency are indeed required; it is hoped that the task status is the same transaction as the queued one | `FOR UPDATE SKIP LOCKED` officially allows multiple consumers of queue-like tables to avoid locks, but it produces inconsistent views and is not suitable for universal consistent reading [R4]. After the acquisition transaction is committed, the row lock no longer protects the entire execution, and persistent lease/heartbeat/fencing and external idempotence are still required |
| Temporal | A large number of long waits, timers, complex multi-step retries/compensations, the team needs to be mature in workflow operation and maintenance and willing to assume service and SDK constraints; triggered by actual faults/development complexity | Workflow relies on Event History/replay to recover; Workflow code must meet determinism, and release uses Worker Versioning or patching (R6 and R8). Activity may still be re-executed and should be idempotent (R7); it cannot replace resource isolation, approval, real process supervision, and third-party effect verification |
Do not mechanically switch Temporal based on "how many minutes the task exceeds", nor do you regard PostgreSQL as a "built-in workflow". Use SQLite durable jobs initially; migrate when write lock waits, queuing delays, multi-host requirements, or complex recovery code pose practical constraints. There is no stress test for this warehouse, and there is no fictitious upper limit on the number of concurrent tasks/database size for SQLite.
**Minimum job contract (design). ** `job_id, workspace_id, trigger_key, payload_ref/hash, due_at, state, attempt, owner, lease_epoch, lease_expires_at, heartbeat_at, retry_policy, last_error, operation_ref`; The unique constraint limits the correct account/connector/trigger domain. SQLite uses short `BEGIN IMMEDIATE` or equivalent atomic get; PostgreSQL locks the candidate and updates the get fact within a short transaction. Do not wait for LLM or network requests within an open DB transaction.
Submit message/command, business status, event/outbox and required successor jobs with the same transaction; dispatched after submission. If the crash occurs when "received but not yet started", it cannot be simply regarded as not started. The stable run/launch ID should be used to query the runner; the runner needs to persistently record the deduplication results of the same launch ID. This mechanism still does not guarantee that uncooperative third-party native protocols are idempotent.
Queue retry only processes actions that are clearly transient and meet safe retry rules, exponential backoff + jitter, maximum attempt/total duration, per-connector circuit breaker and dead letter; auth/conflict/unknown are processed separately. Monitor the oldest due job, expired lease, retry rate, dead-letter and long-term WAL read transactions. When the disk is full/read-only/transaction submission fails, no successful ACK will be sent, and the queue will not continue to be consumed; independent bounded emergency logs/operation and maintenance alarm exits will be retained.
**Durable configuration facts. ** SQLite officially clarifies that WAL+NORMAL may roll back the commit in the event of a power outage/system crash, and the application crash is still durable; FULL increases WAL sync [R1] for each commit. Therefore, the control record defaults to FULL, and the connection configuration is checked to set the database file more than once. Official `fullfsync` defaults to off and F_FULLFSYNC is only supported by Mac; whether it is enabled, performance and target disk guarantee need to be tested in practice. `foreign_keys=ON`, remaining disk space, abnormal fsync return and failure status also need to be started/health checked; the single-process kill experiment cannot be extended to power outage/storage damage proof.
If Temporal is introduced, make it clear **Single Scheduling Owner**: Cylo retains authorization, task projection and auditing; workflow execution progress is responsible for Temporal history, by stabilizing workflow/activity ID mapping; do not let the original SQLite scheduler and Temporal retry the same step at the same time. When a single DB transaction cannot be performed across the two, outbox+idempotent startup/writeback convergence is used; active Workflow definitions are not updated without historical compatibility testing, and permission revocation and cost limits are still checked before each Activity is actually dispatched.
## 4. Unknown results of concurrency, fencing and external effects
**design. ** The resource key covers at least native session, writable checkout, shared business resources (such as email account + folder) and service deployment. The only activity run at the task level does not mean that these resources are exclusive. Epoch increases monotonically and is bound to the host generation, and cannot be rolled back to the old acceptable epoch after backup and restoration. The PID must be matched with the startup time/supervisor ID; the reused PID alone cannot kill the process or confirm recovery.
The database record that the lease has expired only means that "it is no longer trusted to renew the lease" and cannot prove that the old execution has been stopped. At least one of the following must be true before starting a new writer after partitioning: the resource side rejects the old epoch; the gateway revokes the old credentials and the old writer has no passthrough; or it is confirmed that the old process tree and write path/network have terminated isolation. Otherwise, it is better to wait than declare that the task takeover is successful and the data is not overwritten at the same time. The host's local monotonic clock is used for time limits, and the database time is used for centralized lease decisions; recording UTC does not mean that the clock will never jump, and the wall-clock timeout is not used to solely prove execution death during recovery.
**effect ledger (design). ** Persistent before execution `operation_id + canonical_request_digest + target/account + effect_key + grant/policy_version`; reserved budget → authorization and re-verification → record dispatching → call → save provider receipt/query result → confirmed. dispatching is not "definitely sent", and confirmed cannot be established simply because HTTP has been received. The result is uncertain and `unknown`, the last evidence, the query plan and whether to allow retry are saved; the business task enters waiting (effect_unknown).
| Crash/Return Scenarios | Recovery Behavior |
|---|---|
| Can prove that the provider has not been reached and there is no execution opportunity | Safely retry the same operation without changing the effect key |
| The provider returns a persistent success receipt | After checking the receipt, add confirmed and no longer execute |
| The local receipt is not submitted after request timeout/disconnection/success | If the provider supports idempotence, confirm its scope, retention period and parameter semantics before reusing the same key; if it supports query, check it first; if neither is known, manual verification/business compensation |
| Provider asynchronous acceptance | Save native operation/job ID polling or reconciliation, and the business cannot be completed due to 202 |
| Cancellation is interleaved with external success | The actual success and cancellation request time are retained; cancellation does not overwrite the successful effect and can provide new compensation actions |
**fact. ** Stripe officially distinguishes API v1/v2: v1 retains the first execution result (including 500) with the same key. The key can be cleared after at least 24 hours. After clearing, new requests with the same key will be generated; if the parameters are inconsistent, an error will be reported [R12]. This is only used to prove that idempotent protocols have clear boundaries, and does not promote Stripe behavior as email or other provider guarantees. Internal operation/inbox records cannot be deleted arbitrarily based on the provider's short-term key TTL; nor can old tasks be restored by automatically re-issuing the old key alone.
**Temporal boundary facts. **Official description: Completed Activity will not be re-executed in workflow replay, but the Activity will not be recorded in the history before returning/error; failures within this window may cause retry [R7]. Even if the Temporal is changed, the window where the message is successfully sent but the receipt is not persisted still requires the above-mentioned ledger and provider capabilities.
## 5. Approval, removal and isolation
**design. ** Approval is a limited capability for specific actions, not a freely applicable "user said yes". Bind actor/workspace, task/run/plan revision, normalized parameter hash, real target/account/environment, release/config digest, grant and policy version, budget range, expiry and single consumption ID; the same idempotent key and different parameters are rejected. Approval confirmation and consumption adopt compare-and-swap/unique constraints, and dual-device clicks are only valid once. Actions that are low risk and within the scope of existing authorization do not require meaningless repeated approval.
The inspection time point includes at least submission and actual execution; permission changes between the two will invalidate the old approval. Parse the path for file operations and verify the root directory/symbolic link. The path cannot be approved followed by the symlink replaced by the attacker; the domain name allowlist also needs to handle redirect, DNS resolution/IP, localhost/cloud metadata target and tunnel detour. Manifests that cannot force actual access to the scope are only declarations and are not marked as isolation passes.
| Withdrawal phase | Commitable behaviors and limitations that must be exposed |
|---|---|
| Not yet dispatched | The same transaction canceled the grant, expired pending approval, and canceled the command/job pending; subsequent actual tool calls were rejected |
| In transit but passing through the controlled gateway | The gateway rejects new requests/traffic and terminates the request; actions that have been accepted by the provider may still be completed and require receipt verification |
| Offline independent service | Short-term lease/credential expiration stops new effects; the initial TTL of the example is 60 seconds. The actual guarantee depends on resource-side credential invalidation, clock and isolation, and the SLO has not been reached |
| Existing voice direct connection media | The gateway refuses to create/control and requests the client to stop track, close RTCPeerConnection/DataChannel, and record confirmation; deleting binding/withdrawing token does not prove that the existing WebRTC is disconnected, and forcing the server to terminate requires upstream capability testing or controlled media relay |
| The long-term secret has been copied to any program | There is no forced recycling capability for single database changes; remove third-party tokens/rotate, disconnect the network, stop processes/isolate the host. If these actions are not completed, only the cancellation pending confirmation |
**Perform boundary design. ** Git worktree shares warehouse metadata and the process still has the original OS identity; it cannot serve as file/network/process/secret isolation. Standalone OS users are not completely isolated from the network either. The trusted personal local mode can use controlled tools, a minimal environment, and a separate data directory, but its high-trust premise should be clear; the self-generated program is first run in a build/test environment with no production secret, no network by default, read-only dependencies, and bounded temporary directories. The formal service only injects the required SecretRef, minimum account permissions and bounded resources, and actual reading and writing/outgoing are subject to mandatory boundaries.
Linux can evaluate systemd `NoNewPrivileges`, `ProtectSystem`, `ProtectHome`, path allowlist and cgroup resource restrictions; the official has operating prerequisites for specific namespace/permission capabilities [R9], user services and system services cannot be the same by default. The container uses non-root, read-only root, remove capability, seccomp, no host network/PID, no Docker socket and minimum mount; `--network none` officially only creates loopback [R13], and additional controlled exits are set up when external connections are required. Docker officially controls the daemon and can mount the host root and modify files [R14], so the generated code cannot freely construct docker parameters. Strong confrontation/multi-tenant scenarios give priority to independent VMs/hosts; shared kernel containers do not obtain escape security guarantees in this article. Subsequent macOS implementation of isolation/network quota and resource capping has not been verified on a real machine, and the Linux configuration name cannot be copied to claim that it meets the standards.
**CAO special facts and disposition. ** 02 has been fixed `4e990a9d78b154ad76c6cf94c7b51e36fce69f21` (2.5.4); this report is an independent read-only check of the source code: the Codex command contains `--yolo` by default, which is not the authorization mode that Cylo should use by default; `worktree_service.remove_worktree` is clearly `git worktree remove --force` followed by `git branch -d`, so uncommitted/untracked files are discarded, but unmerged submitted branches are not forcibly deleted. [R15]. Do not exaggerate this as deleting all commits.
If CAO is used, change the fixed version of the provider/session route according to [07](07-cao-cli-handoff-plan.md) and verify the final command. The default yolo path is prohibited; the allowedTools in the prompt are not regarded as mandatory policies. Deleting the terminal cannot directly recover the working directory: first prove that all writers are stopped → register tracked diff, binary patch, untracked file list/content hash and necessary ignored products → atomic archive and verify readability → acceptance / retention period → ordinary non-force cleanup. The ignored directory may have secrets or large dependencies, so it should be processed by category and not blindly packaged in the entire directory. Quarantine and capacity alarms will be retained if cleanup fails; any force destruction is an independent, reviewable, path-limited authorization action.
## 6. Auditing, Data Retention and Cost Limits
**Audit design. ** Record command/operation/run, actor and authentication source, workspace/project, host generation/epoch, grant/policy/approval version, input and target digest, provider native ID/receipt, occurrence/observation/submission time, result evidence hash and failure classification. Keep the causal chain of requests, rejections, revocations, changes, exports/deletions, restorations and manual verification. Original sensitive text and audit metadata sub-library/storage permissions; do not put keys, complete audio, email text, authorization header or all environment variables into the log.
Only adding an application audit account does not mean that the administrator cannot tamper with it; the hash chain can only help detect changes, and it can still be completely rewritten without an independent anchor point. High-assurance deployment can use independent additional storage/object locks and independent access control; individual stand-alone machines clearly define their guarantee scope. The retention is configured according to data type (for example: original debugging logs for 7 days, running evidence for 30 days, authorization/decision metadata for longer, all to be determined by user policies), and they are not stored indefinitely. Deletions are propagated to the index/cache/derived memory; backups are retained for a limited time and tombstone is applied after recovery to avoid reviving deleted data.
**Real-time voice credentials and data. **Adopt chatgpt-web-voice real-time upstream/gateway/multi-account pool; account management and open mic decentralization, owner/workspace/project scope under construction session and auxiliary control are verified again. Permanent credential encryption and storage gateway backend, log desensitization, independent backup protection, without handing over voice models or browsers. Accounts in the pool are not sources of Cylo identity or Codex authentication. Only the context required for authorization is sent to the upstream; the current source code is `history_and_training_disabled:false`, and it cannot be claimed that the upstream has no history by default. New cross-account sessions need to check the data range and the upstream copy deletion boundary.
**Cost and resource design. ** ChatGPT voice account subscription fee/observable limit, Codex usage and other model/API fees are split; subscription is not equal to API balance, real minutes/reset point unknown time scale, not successfully deduced by JWT exp or settings/user. Multiple accounts only increase candidate resources and do not constitute an unlimited limit; local call duration is an estimate. Set the number of calls, concurrency, token/cost estimate, retry depth, running time, CPU/memory/PID/disk/log/network/event backlog limit according to workspace/user/project/task/service/provider; atomic reservation before dispatch, and idempotent retry included in the same operation. Cross-Worker derivation cannot create new tasks to bypass the budget, and service calls to Workers inherit a stricter budget; the upper limit of LLM calls and external API, build download, and storage costs are counted separately.
When the budget reaches the top, stop **new distribution** and reserve stop/revoke/alarm control resources; usage is missing and marked as unknown and reserved conservatively, and cannot be treated as 0. When estimating the maximum cost without a provider hard boundary, there is no guarantee of an accurate dollar cap; in-transit calls and post-cancellation billing may result in measurable excess. If a hard cap is required, the provider-side limit, the enforceable upper limit for each call, and the maximum concurrency should be combined. Do not claim that a local counter can cancel the incurred charges. Avoid endless calls to Super to explain budget issues after reaching the budget.
Alarms must be generated deterministically; zero LLM life-saving calls are made when there are no tasks to be processed. Restart storm speed limits and abnormal services have restart budgets; event buffers and notification backlogs have capacity levels. Log rotation/GC must not clean up data that is still referenced by run/release/backup; a part of the disk is reserved for control and recovery, so that even the stop state cannot be accounted for after the product is full.
## 7. Backup, recovery and environment migration
**fact. ** The SQLite Online Backup API creates a consistent copy of the running database [R3]; directly copying the active master db file does not guarantee that all commits containing WAL are copied. PostgreSQL officially distinguishes between SQL dump, file system backup, and continuous archive/PITR [R5]; if you need a smaller RPO, you should evaluate WAL archiving and base backup instead of considering "migrated Postgres" as a backup solution.
**Backup design. ** A manifest is associated with a consistent DB snapshot (schema version/event water level/backup generation), content-addressed product/release, project submitted and uncommitted/untracked necessary files, configuration/trigger/checkpoint, native session supported recovery materials and versions, permissions/credential references, deleted tombstones, and object checksums. Native session files are only backed up within the scope of official support and permissions; it cannot be inferred from restoring a database that the official CLI native session is fully restored with real tools/approvals; official desktop App synchronization is not within the scope.
First form a DB snapshot and reference list, and pin the referenced objects to prevent GC; copy and verify each item before publishing the complete manifest. The backup of missing objects cannot be marked as successful. Executing project files take frozen write/file system consistency snapshots or declare weakly consistent scopes; the database, artifact, and project directory are not naturally one transaction. The secret is encrypted and accessed separately. To restore the key, use independent security materials or re-authorize; encrypted backups without decryption materials cannot be considered recoverable. Keep at least one backup outside the fault domain; RAID, same-disk copy, and Git remote cannot cover all faults and uncommitted results.
**Restore Operation Sheet (Design). **
1. Read the manifest in the isolation environment, verify hash, schema/foreign key, object/directory association, decryption permission and deletion policy; disable all triggering/outgoing at the beginning to avoid actual sending of emails.
2. Generate a new installation/host generation and stream epoch, invalidate old leases and unconsumed approvals; backup authorizations need to be rechecked for identity and validity, and grants that are valid at the time of backup are not considered to be permanently valid.
3. Verify that the old host has been stopped/isolated; otherwise, the writer of the same resource will not be enabled. Simply clearing the lease table and starting a new node will not solve the problem of two active writers.
4. Query the dispatching/unknown near all recovery points and the effects that may have been sent according to the provider's native ID; **There may also be external successes after the recovery point**, and the "to be sent" in the old DB cannot be resent directly. Unable to reconcile, manual verification remains.
5. Rebuild the path mapping and index, reinstall the release that matches the platform, and detect checkpoint compatibility; first run tasks without side effects, confirm status/history/permissions/products, and then enable services and triggers one by one.
6. Record the actual recovery point, data gaps, unknown list, verification results and time consumption before declaring recovery; failed backups cannot silently overwrite the last valid copy.
**Migration design. ** The above process will be reused for the first Linux host change; macOS→Linux will be reserved for subsequent on-demand research. At that time, the architecture/dynamic library/lock file, case path, file permissions, time zone/cron, credential library, OS supervisor and Mac-specific automation will be additionally checked. The logical project ID is retained, and the native path is rebuilt through the checkout mapping; the recoverable definitions and data are migrated, not the process memory. When it comes to Mac-specific capabilities, compatibility gaps must be clarified, and Mac runner will not be included in the initial deployment requirements. SQLite→PostgreSQL exports/verifies/switches according to write-stop logic; avoid unnecessary double writing, event/command/effect IDs remain unchanged, sequence/cursor is re-established with clear epoch, and all leases are checked first and then enabled.
## 8. Recovery contract for tasks, events and notifications
**design. ** Start the recovery sequence: suspend active resource distribution→check runner/supervisor/native runtime→supplementary acquisition results/receipt and original history→mark gap/unknown→rebuild outbox delivery/scheduling→unfreeze safe resources. The service can run independently, but events during the period when the control plane is disconnected must have a bounded persistent spool and a stable source ID; for overflow, the gap must be clear and returned to the source for reconciliation, and "synchronized" cannot be reported even if it is lost.
The business event and status are the same transaction, and the outbox is delivered at least once; the consumer uses the persistent inbox unique key to remove duplication, and the processing status is the same transaction as the cursor. Successful network notification does not mean that the user device has received it, the application has been downloaded, or people have read it. Client snapshots read transactions at the same time as water levels, and increments only apply consecutive serial numbers; permission changes/retention period expiration trigger reset and new authorized snapshots. When the source/provider does not have a persistent cursor, it shows an observable gap and cannot fabricate continuity.
The notification is deduplicated with `logical_event + recipient + policy_version/notification_kind`, and the channel attempt and receipt are saved separately; the server inbox is authoritative, and push only prompts for query. If the delivery is successful but the local receipt is not persisted, it may still be pushed repeatedly; the channel collapse/dedupe is auxiliary and cannot guarantee that people will only view it once. Normal progress is merged, exceptions/required authorization are retained; click on the notification to re-read the task/approval validity, old push cannot carry permanent authorization. The user explicitly canceling the notification and canceling the task are different commands.
## 9. Minimum operation and maintenance SLO suggestions and warnings
The following are the **initial design goals, no pressure test, no statement of failure to meet standards**. Measurement is based on versioned deployment, host online interval and actual count; hibernation/shutdown is listed separately in availability statistics, and is not hidden as success. Security invariants are not compromised in the form of "99% allow one override".
| Project | Initial proposal and measurement caliber | Failure handling |
|---|---|---|
| Reliable reception | ACK after commit; supported single-process fault recovery, number of ACK command/event/job losses = 0; FULL storage prerequisite will be tested separately | Any loss is the highest priority fault, stop claiming reliable reception |
| API/Synchronization | Normally open host monthly availability target 99.5%; model-free/externally dependent command ACK p95≤1 second, foreground status synchronization p95≤5 seconds | Over-standard alarm for 5 consecutive minutes; distinguish DB lock, disk, network and offline host |
| Dispatchable queue | When there are resources and the authorization/budget is valid, due→receive p95≤5 seconds; the oldest job>60 seconds alarm | Queue starvation/lease massive expiration troubleshooting, unknown effects do not rely on strong retry to clear the backlog |
| Health and Recovery | Heartbeat example 20 seconds; missing mark unknown (≤60 seconds) three times in a row, not marked healthy; start reconcile within 60 seconds after the control service is restarted | Make it clear that the host is offline; active records that have not converged in 10 minutes are upgraded and processed manually |
| Withdrawal | New distribution = 0 after the online gateway confirms the revocation; Example of the maximum authorized TTL for controlled offline services is 60 seconds; Independent reconciliation of sent requests | Long-term secret services that cannot honor TTL do not claim bounded forced withdrawal rights |
| Side effects | For clear idempotent/reconciliable fixtures: repeat effect=0; all intentionally created unknown windows are visible and are not blindly replayed | Any repeated high-risk effect stops the connector from automatically retrying |
| Notifications | Important events → persistent inbox p95 ≤ 5 seconds; first delivery attempt when provider is available p95 ≤ 30 seconds; logical inbox duplication = 0 | push arrival/read are counted separately, long-term undelivery is visible in the inbox and alternative channels are supported |
| Backup recovery | Personal starting point RPO ≤ 24 hours, control data RTO ≤ 2 hours (starting from valid backup and voucher availability); total recovery of large products is additional | Backup age > 26 hours / verification failure alarm; monthly and isolation recovery drills before high-risk schema release |
| Cost/Resources | 24-hour idle normal maintenance LLM call = 0; new model dispatch after exceeding the budget = 0; estimated/actual/unknown can be checked | separate record of excess in transit; disk <20% warning/<10% stop new large products, only examples can be adjusted |
The database crash recovery objective is not the same concept as the disaster RPO: FULL is designed to withstand synchronized commits on supported storage, and full disk damage is still affected by the backup interval. The final delivery of notifications to the device and email provider is not an SLO that a stand-alone service can alone guarantee.

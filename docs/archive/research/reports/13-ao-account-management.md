# AO Codex Multi-Account Management and Automatic Pool Boundaries

Reviewed: 2026-10-21. AO means **OrchestratorInc/agent-orchestrator (Go)**, not AWS CAO. The user selected AO; this report assesses account capabilities and gaps only and does not reselect the orchestrator.

## Conclusion

**AO already has real management for multiple ChatGPT/Codex subscription accounts. It can save multiple logins, set the default account for new sessions, bind different Workers to accounts, and explicitly switch an existing session to another account. It is therefore inaccurate to say “AO has no account pool, so CLIProxyAPI must be installed.”**

However, if “account pool” means **automatically choose another usable account and continue a task when quota is exhausted/429 occurs**, this fixed AO version **is not sufficient**. It has an account directory, quota display, session binding, and account-switch execution. No cross-account automatic selection, rotation/load balancing, exhausted-account cooldown, or automatic failover scheduler was found. Its “automatic recovery” retries a failed message after the user enables it and the **originally bound account** quota resets; that is not automatic account switching.

Recommendation: first reuse AO's native account capabilities. If automatic rotation is needed, compare “add account scheduling in Cylo on AO” with “route Codex requests through CLIProxyAPI's request-level pool.” The latter is an optional upstream gateway; it does not directly replace AO session/task recovery. See the separate report for the CLIProxyAPI source review. This report does not claim its integration has been accepted.

## Keep the two account surfaces distinct

This SHA has two API groups; do not describe them as “one globally active account determines all Workers”:

1. **`/api/v1/agents/accounts`: session account directory.** Covers Claude/Codex; account homes are under AO state dir `agent-accounts/<provider>/<id>`. Supports setting a default and switching the account on a session with `PUT /agents/accounts/sessions/{sessionId}`. The daemon constructs `agentaccounts.Service` and wires it to the session manager and Chat quota reads; see [daemon wiring](https://github.com/OrchestratorInc/agent-orchestrator/blob/7c83bd68c1e60c85b6a90e3ffa1340c859e4a3ff/backend/internal/daemon/daemon.go#L523) and [constructor](https://github.com/OrchestratorInc/agent-orchestrator/blob/7c83bd68c1e60c85b6a90e3ffa1340c859e4a3ff/backend/internal/daemon/daemon.go#L1366).
2. **`/api/v1/agents/codex/accounts` and `.../account-switches`: managed Codex credential slots / device-global credential switching.** Includes import/check, login, capacity, SSE, a persistent switch journal, idempotency, and a global admission gate. The coordinator explicitly states **“existing controllers outside transaction”; it only changes and verifies the device credential.** Thus a successful global switch does not mean all live Workers were switched. Global switching requires file-backed credentials; unsupported cases such as keyring return a typed error. See [controller](https://github.com/OrchestratorInc/agent-orchestrator/blob/7c83bd68c1e60c85b6a90e3ffa1340c859e4a3ff/backend/internal/httpd/controllers/codex_accounts.go#L43) and [coordinator](https://github.com/OrchestratorInc/agent-orchestrator/blob/7c83bd68c1e60c85b6a90e3ffa1340c859e4a3ff/backend/internal/service/agent/codex_account_switch_coordinator.go#L121).

AO cloud accounts/device pairing, daemon API password authentication, GitHub/GitLab OAuth/MCP OAuth, and model-provider configuration have separate purposes and are not part of a ChatGPT upstream account pool. Evidence for native account support comes from real credential homes and account lifecycle, not merely fields named account/provider.

## Login and CODEX_HOME: credential isolation, shared history

The session-account adapter logs in to Codex with `codex login --device-auth`, allowing the user to select a ChatGPT account in a browser. `Identity` treats it as a subscription login only if app-server reports authorization and `Method == chatgpt`. `LaunchEnv` sets a separate `CODEX_HOME` and clears `OPENAI_API_KEY`, `CODEX_API_KEY`, and `CODEX_ACCESS_TOKEN` when present in the daemon, so a host API key cannot override the selected subscription login. See the [implementation](https://github.com/OrchestratorInc/agent-orchestrator/blob/7c83bd68c1e60c85b6a90e3ffa1340c859e4a3ff/backend/internal/adapters/agentaccount/codex.go#L42).

A separate managed-slot login entry has an internal `ao codex-login` menu supporting ChatGPT browser login, device auth, API key, and access token, and sets `cli_auth_credentials_store="file"` for managed homes. Do not generalize API-key support in this entry to mean the session subscription-account entry accepts any upstream identity. See the [login menu and argv](https://github.com/OrchestratorInc/agent-orchestrator/blob/7c83bd68c1e60c85b6a90e3ffa1340c859e4a3ff/backend/internal/cli/codex_login.go#L29).

AO does not copy a completely independent Codex history for every account:

| Kept private inside each account | Linked to the computer/device Codex home |
|---|---|
| `auth.json`, `models_cache.json`, `tmp`, `log`, `memories`, `app-server-control`, `app-server-daemon`, `ipc`, some global UI state, etc. | `sessions`, `archived_sessions`, `sqlite`, `shell_snapshots`, `worktrees`, `skills`, `plugins`, `cache`, `logs`, `mcp-oauth-locks`, `thread-writer-locks`, `config.toml`, `history.jsonl`, etc. |

Evidence: [shared/private list and Prepare](https://github.com/OrchestratorInc/agent-orchestrator/blob/7c83bd68c1e60c85b6a90e3ffa1340c859e4a3ff/backend/internal/adapters/agentaccount/codex.go#L15), [link and history migration rules](https://github.com/OrchestratorInc/agent-orchestrator/blob/7c83bd68c1e60c85b6a90e3ffa1340c859e4a3ff/backend/internal/adapters/agentaccount/share.go#L20). A missing shared target is created; content is moved from the account side when only it has content. A non-empty local copy is not directly deleted. Thus, visibility of native history still needs preflight evidence; existing directories are not unconditionally merged. Failure to create sharing returns `ErrAgentAccountUnshared`; before switching, AO also checks for history by native ID.

Shared history supports `codex resume <native-id>` across accounts. A private daemon-control directory prevents accounts from attaching to the same app-server by mistake. Shared `thread-writer-locks` plus session transition aim to keep one live writer per conversation. Different Workers/threads can run concurrently, but this provides neither per-account quota reservation/fairness nor multi-tenant data isolation. Shared `config.toml` also means proxy/base_url changes may affect multiple account homes; check the actual configuration boundary during deployment.

## What happens when quota is exhausted

[Chat `usage_limit.go`](https://github.com/OrchestratorInc/agent-orchestrator/blob/7c83bd68c1e60c85b6a90e3ffa1340c859e4a3ff/backend/internal/service/chat/usage_limit.go#L44) imposes these limits:

- `SetTurnAutoResume` is enabled for one failed human prompt, not as a session-wide automatic policy. It requires Chat mode, a recoverable failure, known `ResetsAt`, a valid branch, and explicit delivery record.
- AO does not resend a model request before the deadline. At the deadline it reads quota for the **bound account**, delaying only to a known reset. An account change ends that auto-recovery intent; it does not silently switch to another account.
- It uses 4 recovery workers and a 30-second transient-failure backoff. These are retry-scheduling limits, not account-pool concurrency leases or an exhausted-account cooldown table.
- Recovery reuses durable retry/idempotency and branch checks. Manual retry, account migration, or a new message may consume/cancel the original intent. Unknown reset time is not guessed.

Related source tests: [bound account and deadline](https://github.com/OrchestratorInc/agent-orchestrator/blob/7c83bd68c1e60c85b6a90e3ffa1340c859e4a3ff/backend/internal/service/chat/usage_limit_accounts_test.go), [concurrent recovery](https://github.com/OrchestratorInc/agent-orchestrator/blob/7c83bd68c1e60c85b6a90e3ffa1340c859e4a3ff/backend/internal/service/chat/usage_limit_concurrency_test.go). TUI has quota hints/failure detection, but that does not establish that Chat's retry service applies to TUI.

Review of account selection, switching, quota/429, frontend account hooks, and quota-recovery call paths found no trigger that automatically chooses another account. The conclusion is “no such implementation found in this fixed version,” not a promise about future versions or runtime acceptance based on a source-search miss.

## Effect on Workers and session recovery

An explicit account switch does not transparently move an in-progress streaming request to another login. AO validates the target account and history, performs available checks while the original process is running, drains the current turn or interrupts it, stops the original process, resumes the same native conversation under the target account, and commits the binding on success. On failure it restarts the old account. An interrupted Chat turn is marked `account.switched`; it is not represented as a completed original request. See [transition](https://github.com/OrchestratorInc/agent-orchestrator/blob/7c83bd68c1e60c85b6a90e3ffa1340c859e4a3ff/backend/internal/session_manager/agent_account.go#L13) and [interruption record](https://github.com/OrchestratorInc/agent-orchestrator/blob/7c83bd68c1e60c85b6a90e3ffa1340c859e4a3ff/backend/internal/service/chat/account_switch.go#L13).

Resuming the same thread does not prove that the last shell command, commit, or remote write had no side effect. Cylo must retain task/run, last confirmed step, and unknown-side-effect status to decide whether to continue or retry a failed prompt. Do not replay a whole task on any 429, and do not mark a run complete because account switching succeeded.

Deleting an account first stops agents running under that account; deletion is rejected if a session is starting, to avoid removing a home it is reading. Account records and session bindings persist. Account directories, shared device history, and SQLite need backup within the same deployment boundary; a worktree alone is not enough for recovery.

## macOS / Linux scope

The session-account adapter/service has no macOS-only build tags or runtime restriction; the daemon always constructs the Codex account provider. Its symlink and permission handling targets ordinary Linux/macOS filesystems. The native CLI must exist and app-server protocol must expose required account/capacity methods; device authentication/browser interaction still needs to occur. A headless Linux host can use device auth, but no real login was performed this round, so no claim is made that every deployment or keyring combination has been verified.

The file-store requirement for global managed switching and separate homes for session accounts are two distinct conditions. An older Codex binary missing capabilities, login policy restrictions, or an unshareable home can cause failure. AO has unknown/unsupported states; do not display all of them as “quota available.”

## Can each account have its own network proxy?

**No native per-account network-proxy configuration was found in this fixed AO version.** `AgentAccount` contains only ID, Provider, Home, Email, Plan, and CreatedAt; the account API has no proxy field. Codex `LaunchEnv(home)` sets only `CODEX_HOME` and clears credential overrides. It does not set `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, or `NO_PROXY` by account. Evidence: [data model](https://github.com/OrchestratorInc/agent-orchestrator/blob/7c83bd68c1e60c85b6a90e3ffa1340c859e4a3ff/backend/internal/domain/agent_account.go#L41), [launch environment](https://github.com/OrchestratorInc/agent-orchestrator/blob/7c83bd68c1e60c85b6a90e3ffa1340c859e4a3ff/backend/internal/adapters/agentaccount/codex.go#L56), [account API](https://github.com/OrchestratorInc/agent-orchestrator/blob/7c83bd68c1e60c85b6a90e3ffa1340c859e4a3ff/backend/internal/httpd/controllers/agent_accounts.go#L58). The public snapshot/context for the managed Codex slots also has no per-account proxy field.

AO supports project environment variables, and native processes can inherit the host environment. A process proxy can therefore be configured by deployment/project, but AO does not provide “account A always uses proxy A, account B always uses proxy B.” Nor does this prove that auxiliary identity probes, quota reads, or relogin processes follow a project proxy. [`runtimeEnvChecked`](https://github.com/OrchestratorInc/agent-orchestrator/blob/7c83bd68c1e60c85b6a90e3ffa1340c859e4a3ff/backend/internal/session_manager/manager.go#L6059) assembles project environment before merging account environment; the [account client](https://github.com/OrchestratorInc/agent-orchestrator/blob/7c83bd68c1e60c85b6a90e3ffa1340c859e4a3ff/backend/internal/adapters/chatdriver/codexappserver/account.go#L85) separately starts app-server by home. Whether each process uses a proxy also depends on local Codex support for the relevant environment/protocol; this was not tested.

`model_provider` / `base_url` identifies the model API destination; it is different from an HTTP/SOCKS network egress proxy. AO session-account homes share `config.toml` by default, so separate `CODEX_HOME` values alone do not prove each account has a separate provider/base_url. Editing that shared file can affect every account. Even separate endpoints do not prove login and token refresh use separate network egress.

If AO-native accounts are retained, the minimum change is to persist controlled proxy configuration per account and inject it consistently when starting TUI, Chat host, login terminal, identity/quota probes, and refresh-related native processes. Also handle case variants of environment variables, `NO_PROXY`, host proxy overrides, and proxy-credential redaction. Pre/post-switch helper checks must use the target account proxy too; adding env only to the final Worker is insufficient. Extend `AgentAccountProviderCLI`/`CodexAccountContext` with account context; do not modify daemon-global environment in a way that lets concurrent accounts overwrite each other. This is a proposal; AO does not provide it now.

## Where to add automatic rotation in Cylo

| Route | Suitable goal | Still to implement/accept |
|---|---|---|
| **AO native accounts + Cylo scheduler** | Keep official Codex TUI/Chat, real ChatGPT login, native history, and observable per-Worker account ownership | Account allowlist/budget, model/plan compatibility, health/quota, concurrency leases, reset cooldown, session affinity, switch limit; reuse `StartAccountTransition` and verify the same native ID before safe continuation |
| **AO runs Codex + CLIProxyAPI request-level pool** | Let one compatible API gateway select among multiple upstream identities and share pool policy across clients | Check Codex custom-provider/Responses/stream/tool/model compatibility; validate failover/session affinity, midstream errors and duplicate tool side effects, quota attribution. AO's ChatGPT account panel no longer identifies the proxy's actual upstream account. |

First test a minimal version of the first route: two isolated test accounts or simulated account adapter, two independent Workers, and one account preconfigured as exhausted. The scheduler leases an available account and starts a durable transition only for affected sessions. Check that the old writer stopped, native ID stayed the same, unknown side effects were not replayed, and rollback on failure did not lose the worktree. Then test that simultaneous exhaustion on one account does not make every Worker race for the same backup account. Real-account acceptance is later; it was not performed here.

Account scheduling can initially be a Cylo component that calls AO APIs, reducing changes to AO core. Introduce CLIProxyAPI as a separate service only if the main need is routing model requests for multiple clients. Do not let AO and the proxy independently choose the upstream identity for the same session without coordination.

## Difference from Space's web real-time voice pool

Space handles web real-time voice login/media connections, audio streams, and interruption. AO here manages **Codex/Claude CLI subscription logins and coding sessions**. Even if both involve ChatGPT accounts, do not infer that tokens, credential homes, WebRTC sessions, quota classification, locks, or recovery methods are interchangeable.

Cylo should maintain two resource ledgers: AO/Codex account policy for orchestration Workers, and Space's real-time voice accounts/connections for the voice gateway. They exchange task commands and events. Adding CLIProxyAPI does not replace Space's web real-time voice pool or establish session migration for it.

## Unverified items

Real multi-account ChatGPT subscription login, concurrent refresh-token updates, upstream plan/model compatibility during cross-account recovery, headless Linux device login, account/capacity APIs across Codex versions, and behavior of shared SQLite/locks under high concurrency or crashes were not runtime-tested. Source recovery/rollback tests do not replace those checks. “Supported” above means the fixed version has explicit implementation and daemon wiring; production still needs account and process-recovery slices.

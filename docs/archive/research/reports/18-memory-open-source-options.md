# Cylo Long-Term Memory: Boundaries Between Open-Source Components and Cylo-Owned Policy

Reviewed: 2026-10-21. Conclusion: **implement Cylo's memory business API in Go, reuse open-source extraction/retrieval components, and use a Memory Agent on demand for complex curation; do not adopt a complete memory platform yet.** Mem0 can handle general extraction/retrieval and can be used as an agent tool. Using it does not remove curation responsibilities or require running another agent. Python alone is not a reason to exclude it. Graphiti fits a later need for temporal knowledge graphs. Letta currently overlaps AO's agent-runtime responsibilities, and its Cloud shared-memory feature must not be confused with local open-source capability.

“Build it ourselves” here does not mean reimplement a vector database, embedding model, or general retrieval engine. It means implementing Cylo-specific source-of-truth, confirmation, scope, permission, update, and deletion rules. A vector store can provide an index; it is not a complete memory system. There is no product implementation yet. The following is a selection recommendation, not a delivered capability.

## Scope and pinned versions

Only three distinct candidates were selected: lightweight-integration Mem0, temporal-graph Graphiti, and Letta, a complete agent harness with memory. No matrix of similar platforms such as MemOS was added, and no unread Go project was presented as a mature replacement. The conclusion is not that “Go has no memory libraries.” Go stack consistency is an operations cost factor, not the sole selection criterion.

## Mem0: saves substantial work, but Cylo still needs a control layer

The pinned source's [Memory implementation](https://github.com/mem0ai/mem0/blob/2c81af3bbe27d9bccb09c772d583df9e9be72ee5/mem0/memory/main.py) already has these real capabilities:

- `add()` / `_add_to_vector_store()` retrieves related existing memories and recent messages, uses an LLM to extract facts, batches embeddings, deduplicates by hash, and writes to vector storage. **The default is additive extraction, not the automatic ADD/UPDATE/DELETE decision flow often described in older articles.** Explicit `update()` / `delete()` still exist.
- `search()` provides scope filtering, semantic retrieval, and additional retrieval logic in this version. `get_all()`, `history()`, and `delete_all()` are available for integration; Mem0 should not be described as only a vector-database wrapper.
- `_update_memory()` / `_delete_memory()` and [SQLiteManager](https://github.com/mem0ai/mem0/blob/2c81af3bbe27d9bccb09c772d583df9e9be72ee5/mem0/memory/storage.py) record old/new values, ADD/UPDATE/DELETE, time, and actor/role. This saves work on summaries, extraction, indexing, and history.

Four material constraints matter for Cylo:

1. **Isolation is not authorization.** At least one of `user_id`/`agent_id`/`run_id` is required. During writes, `search_filters` for retrieving existing memories retains only these three IDs. `metadata.project_id`, even if usable for read filtering, cannot by itself isolate write-time extraction and deduplication context. Cylo should generate controlled scope IDs (a project scope can map to a database-local ID) and not treat “executor Agent ID” as the only shared boundary. Cylo merges global, project, and task results. The server must also authorize callers for ID-based update/delete/history.
2. **Edit history is not an authoritative decision version.** Metadata can include sources such as `source_event_id`, but default extraction does not create a per-fact evidence chain citing original message segments, nor does it classify confirmed/executed/inferred facts, record who confirmed them, or relate superseding decisions. Text-change history cannot replace these business rules.
3. **Deletion does not erase all source text.** `_delete_memory()` removes the vector but writes the old text into DELETE history; recent messages are separately saved in SQLite, and entity cleanup is marked non-fatal. Complete deletion must also address history, original messages, entity indexes, backups, and reconstruction inputs. Calling the delete API alone cannot promise completion.
4. **An in-process lock is not a cross-store transaction.** SQLiteManager uses `threading.Lock`. Vector writes and history writes happen in separate steps; no atomic commit across them or complete cross-process serialization per scope was found. Cylo needs idempotent events, a same-scope write queue, retry/rebuild behavior, and protection against concurrent extraction overwriting or duplicating results.

The local library is not bound to an agent runtime, so it can provide consistent retrieval to different AO executors. Migration must export payloads, history, source evidence, and configuration; changing embedding models requires rebuilding vectors. The [OpenAI LLM](https://github.com/mem0ai/mem0/blob/2c81af3bbe27d9bccb09c772d583df9e9be72ee5/mem0/llms/openai.py) and [embedding adapter](https://github.com/mem0ai/mem0/blob/2c81af3bbe27d9bccb09c772d583df9e9be72ee5/mem0/embeddings/openai.py) support a configurable base URL, but CLIProxyAPI's chat routing does not prove that it also provides the required embedding service; select an embedding provider separately. `infer=False` skips LLM fact extraction but still calls embeddings, so it is not a zero-model mode.

**When to introduce it:** If the first release requires automatic preference/fact extraction, continuous background curation, or semantic recall, use Mem0 OSS behind a controlled worker from the outset to reduce implementation cost; allow it to write only derived candidate memories, while Cylo stores confirmed decisions. If the first release can start with explicit memories, raw history, confirmed decisions, and source lookup, defer the Python service and keep an adapter boundary in the API. This neither promises to rewrite Mem0 later nor calls for first building an equivalent general-purpose extraction engine by hand.

## Graphiti: stronger source/time relationships, with clearer costs

The [Graphiti API](https://github.com/getzep/graphiti/blob/8e320f880e7d169a907dbf2a7ac4188586c03b55/graphiti_core/graphiti.py) builds entities and relationships with `add_episode()` / `add_episode_bulk()`. `search()` / `search_()` provide hybrid retrieval, graph-proximity ranking, filters, and more. [EpisodicNode](https://github.com/getzep/graphiti/blob/8e320f880e7d169a907dbf2a7ac4188586c03b55/graphiti_core/nodes.py) stores raw content and `source_description`; [EntityEdge](https://github.com/getzep/graphiti/blob/8e320f880e7d169a907dbf2a7ac4188586c03b55/graphiti_core/edges.py) has episode source sets and `valid_at`/`invalid_at`/`expired_at`. It can reduce work to represent when a fact was valid and which material supports a relation; it should not be reduced to graph search alone.

- `group_id` / `group_ids` provide partitioning. This version's `_resolve_request_scope()` specifically avoids concurrent requests reusing a shared driver across groups. Cylo must still authorize on the server; calls that omit `group_ids` are not a safe default.
- `remove_episode()` removes the source, keeps edges supported by other episodes, removes nodes/edges supported only by that source, and tries to rebuild surviving entity summaries. **Rebuilding invokes an LLM; if it fails, the old summary is restored and logged.** Do not claim deletion automatically cleans all derived content. Group/UUID delete methods also exist.
- It provides async, bulk, and semaphore concurrency limits, but the source says the limit applies per `gather` call. It is not a global throughput lock or proof of transactional behavior across every ingestion/deletion operation.
- The graph is not tied to AO or a particular agent runtime. Graphs and episodes can be exported; changing databases involves graph queries/indexes and model migration, so it is not equivalent in cost to moving ordinary JSON.

LLM entity extraction/disambiguation, embeddings, optional reranking, and graph storage add operating costs. Neo4j is not the only option: dependencies also list FalkorDB/FalkorDBLite. The Kuzu extra is marked upstream-unmaintained and planned for removal; **do not recommend the older Kuzu setup for a new lightweight deployment.**

Introduce Graphiti when real tasks repeatedly need cross-entity, multi-hop, temporal retrieval that ordinary metadata plus full-text/vector search cannot satisfy. Graphiti can represent “when the SQLite decision was replaced by PostgreSQL,” but Cylo decides whether the relationship was formally confirmed by a user; graph inference cannot automatically update an authoritative decision.

## Letta: current Git-based memory, but shared capability differs between Cloud and local

The current [README](https://github.com/letta-ai/letta-code/blob/f1627b01605780872677cd6af8d4b3a8d13b1cdb/README.md) describes a stateful agent harness: memory blocks, MemFS, background learning, App Server, interactive terminal, and more. A local mode exists; do not say it is cloud-only. Its memory is Git-tracked, readable/writable text files with traceable commit history. The [memory subcommand](https://github.com/letta-ai/letta-code/blob/f1627b01605780872677cd6af8d4b3a8d13b1cdb/src/cli/subcommands/memory.ts) supports export, and [memory-repository](https://github.com/letta-ai/letta-code/blob/f1627b01605780872677cd6af8d4b3a8d13b1cdb/src/cli/commands/memory-repository.ts) can configure an external Git repository.

However, [shared-memory.ts](https://github.com/letta-ai/letta-code/blob/f1627b01605780872677cd6af8d4b3a8d13b1cdb/src/cli/subcommands/shared-memory.ts#L249) explicitly rejects the local backend: `Shared memory requires a Letta Cloud agent; the local backend does not support it.` The open-source client has organization repository create/list/attach/detach/history calls and local-mount logic; that does not prove the complete shared backend is open source and self-hostable. Detach explicitly leaves the local mount in place, and deleting a Git file also leaves history.

[memory-confinement](https://github.com/letta-ai/letta-code/blob/f1627b01605780872677cd6af8d4b3a8d13b1cdb/src/memory-confinement.ts) isolates file access for unattended memory subagents. This is a permission boundary in the Letta harness, not Cylo's project/task authorization. Go can reuse exported data or text conventions. Adopting the full system adds another agent lifecycle, runtime, context, and authentication integration. This round did not run the local App Server and makes no runtime acceptance claim about consistency of Git writes/deletes across processes.

Therefore, do not select Letta as Cylo's first-release memory service. If Letta is later selected as an executor under AO, its native memory remains that executor's context and cannot be the sole fact store for every agent.

## What AO already provides, and what is missing

It is not true that “AO has no memory at all”: the fixed version has durable session/conversation history, native session recovery, agent-switch handoff, and history references. For example, [handoff_note.go](https://github.com/OrchestratorInc/agent-orchestrator/blob/7c83bd68c1e60c85b6a90e3ffa1340c859e4a3ff/backend/internal/domain/handoff_note.go) builds a bounded handoff note from the original task, recent conversation, changed files, and native-history path. [side_context.go](https://github.com/OrchestratorInc/agent-orchestrator/blob/7c83bd68c1e60c85b6a90e3ffa1340c859e4a3ff/backend/internal/service/chat/side_context.go) can freeze and inherit conversation excerpts.

This review checked `backend/internal`, HTTP routers, SQLite migrations/stores, and matches related to memory/embedding/vector/knowledge. **No unified service was found for long-term fact extraction, authorized retrieval, confirmed versions, and deletion across agents/tasks and global/project/task scopes.** Codex adapter `MemoryCitation`/`ThreadMemoryMode` in its protocol is native-runtime functionality, not an AO-built shared-memory API. This is a source conclusion for the fixed version and checked scope, not a claim that AO will never add this capability. Cylo should reuse AO history/events as sources and provide a unified business-memory layer; it need not rewrite AO session recovery.

## Recommended first-release ownership

Cylo's Go layer owns scope/authentication, raw events and sources, confirmed fact/decision versions, explicit memory APIs, deletion policy, context budget, and unified integration for executors. Relational storage holds authoritative records; full-text and later vector indexes are rebuildable derivatives. SQLite is a viable single-machine first-release candidate, not a commitment to a future multi-writer architecture. Chinese segmentation, short terms, mixed Chinese/English, and semantic recall require separate acceptance; the existence of an FTS table does not mean Chinese retrieval meets the bar.

PRD §10.3 says a Memory Agent “may” be used; it does not require a separate role. Curation responsibilities include recognizing long-term information, extracting facts, organizing project history, establishing links, finding duplicates/stale/conflicting material, and proposing updates. Summaries, duplicate-candidate merging, and complex retrieval support those duties; they cannot silently merge conflicting confirmed facts. Explicit memory/decision registration, authorized versioning, rule-based deduplication, and ordinary retrieval belong in the Go API and rules. Mem0 can provide general extraction and semantic search. A separate agent mainly adds cross-record historical review, semantic conflict/staleness judgment, linking, and complex project summaries. Enable a background curation role when its value is demonstrated, dispatched by Super or an AO event/scheduled task; do not make it a first-release prerequisite or block every conversation on it. A dedicated responsibility does not require a separate agent, and does not require a permanently running process. Runtime/model remains configurable; do not pin it to Codex.

For complex curation, use **Cylo / Super → Memory Agent (on demand) → Cylo Memory API → Mem0 / SQLite**. The Go API enforces scope, permission, source, version, and persistence rules; Mem0 handles replaceable extraction/retrieval steps; SQLite stores authoritative Cylo records. Quick queries and authorized writes of explicit user memories/decisions may go directly to the API without blocking on a Memory Agent. Record explicit decisions with their source and do not ask for the same confirmation again. Agents share only memories within their task authorization; do not expose a Worker's private history by default.

Avoid having an agent extract a source and then having Mem0 extract it again by default. Delegate general extraction directly to Mem0; use a controlled adapter to skip duplicate extraction for already curated candidates. In the pinned version, `infer=False` skips the fact-extraction LLM but still calls embeddings; deterministic events use rules/API.

Start with mature open-source storage/full-text components. If automatic extraction or semantic retrieval is needed in the first release, use a Mem0 worker rather than expanding a custom general memory engine. The API/job layer serializes/idempotently controls writes per scope. A Memory Agent produces candidates, sources, and conflict warnings; deterministic updates and records with existing explicit authorization are committed by rule. It does not block the Space real-time voice critical path and receives no extra power to change permissions, task state, or formal decisions. Account pools and CLIProxyAPI are model-access layers, not memory-scope managers; provider accounts are not user/project identities. See [17 memory design](17-memory-requirements-and-design.md#responsibilities-of-the-memory-agent-super-api-and-engine) for full responsibility boundaries.

Before adopting any engine, test the same small set of samples: sharing across agents within one project and isolation across projects; old/new decisions from SQLite → PostgreSQL with sources; inference cannot override confirmed facts; event retries/concurrent writes create no duplicates; history/index/source deletion follows the agreed boundary; restart recovery and export/rebuild; Chinese retrieval. No real model/account was used this round, so semantic quality and end-to-end integration have not passed acceptance.

## Review record

Fixed-source file SHA-256 values, candidate versions, and local checks without a model are in [memory-open-source-options-evidence.json](../evidence/memory-open-source-options-evidence.json). The only runtime check directly loaded Mem0's standard-library SQLiteManager file and verified history retention for ADD/UPDATE/DELETE and concurrent writes. Static source review is not full runtime acceptance of a candidate platform.

# Apple clients

Cylo provides native SwiftUI apps for macOS, iPhone, and iPad. The clients use the Go server as the authority and keep offline snapshots visibly stale after connection validation. Product flows, voice and notification boundaries, current build evidence, and device acceptance are maintained in the [master plan](../../docs/master-plan.md#4-native-application-flows).

On first connection, enter the server URL and its shared 32-byte base64url instance key. The client also imports QR images locally on macOS/iPhone/iPad and opens `cylo://connect?server=<URL-encoded>#key=<key>` installation links. On iPhone/iPad, Scan QR code opens the camera and requests permission at that action. Scanning or explicitly importing a QR image connects with the validated address and key; opening an external installation link populates a review form and still requires Connect. There is no built-in server address or saved-server list. Settings show the active address, reconnect, replace its key, or clear the connection before moving to a different server. All credentials use Keychain, scoped to the normalized server URL.

A successful authenticated snapshot opens the workspace. Rejected credentials close access; ordinary connection failures preserve an already validated workspace with stale-state feedback. Replacing or clearing a connection removes its key, local queued commands, snapshots, and drafts; it does not revoke the shared key or stop server tasks. Notification registration uses an independent installation UUID, so sharing the instance key does not collapse multiple devices into one push target. Image import uses only selected images and requires no camera permission. Camera scanning decodes frames locally without saving or uploading them; switching to a different saved server still requires clearing the existing connection first.

Complete app-target builds require an eligible Xcode destination. Direct SDK compilation provides source-level evidence only. Build, signing, device, APNs, and live voice acceptance must be reported separately; no source check establishes those outcomes. See [milestones and acceptance](../../docs/master-plan.md#12-milestones-and-acceptance) for the evidence boundary.

The redesigned workspace is shared by recent tasks, task search, projects, and linked notifications. On iPhone, Conversation, Tasks, and Projects are tabs; on macOS and regular-width iPad they are sidebar destinations. Open notifications from the toolbar and Settings, Memory, or Capabilities from the account menu. Push preferences are in Settings. Voice opens from the composer; review the transcript draft before submitting.

The macOS assistant uses compact project/task navigation, a bottom composer with a prominent microphone, and a collapsible task activity rail on wide windows. Tasks show progress, results, evidence summaries, and decisions. The [approved visual direction](../../docs/design/native-assistant-reference.png) is a design preview; native visual and interaction acceptance remain open.

The [visual reference](../../docs/design/apple-redesign.html) is a standalone design artifact. It does not replace native screenshots or device validation. The current redesign verification and remaining acceptance boundaries are recorded in the master plan.

For operator-controlled Xcode access from another host, use the repository's [Xcode MCP over SSH skill](../../.agents/skills/xcode-mcp-ssh/SKILL.md). It includes connection discovery, a batch helper, and real-device startup troubleshooting.

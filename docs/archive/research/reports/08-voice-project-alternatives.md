# Comparison of voice project alternatives: which ones are better and which ones cannot be replaced
Verification date: 2026-10-21. Read first and use [03 Speech Implementation Plan](03-voice.md), [06 Independent Review](06-realtime-integration-review.md) and [Speech Evidence](../evidence/voice-realtime-audit.md). The goal is still **ChatGPT web account real-time two-way voice + gateway + multi-account pool + Cylo Super execution closed loop**, covering browsers/mobile phones and interrupts. This article only does research, and does not modify the main line, access accounts, or write product runtime.
**Conclusion: This round of search did not find a better direct alternative that has been verified. ** Among the candidates of the same protocol, the Python original author version has a disconnection/limit event reconnection entry that is worth learning from, but it does not solve the real quota scheduling, and may even keep re-selecting the depleted account. **LiveKit Agents and Pipecat are stronger in terms of programmable business closed loop, rounds and playback control**; they are another layer of infrastructure. Existing plug-ins cannot directly connect to ChatGPT web tokens, nor do they come with their own account pool for this requirement. If you stick to the existing upstream, your first choice is to continue to enhance the Space gateway; if you accept changing the upstream protocol, credentials and commercial billing in the future, then compare LiveKit / Pipecat, this choice cannot be accepted by the user by default.
## 1. Similar gateways and infrastructure must be compared separately.
Class A follows the ChatGPT web page `/realtime/wm` and Web `access_token`, and the browser directly connects to the upstream WebRTC. Class B is responsible for the Agent, media, turn/tool ​​life cycle, and can use the native speech-to-speech provider without going through STT→LLM→TTS**, but ready-made access usually requires corresponding provider API credentials. The fact that class B has function calling does not prove that the private `client_tools` of class A is available; the completed event of the official API protocol does not prove that the web subtitles have the same final semantics.

## 3. Why Class A is not enough to replace Space
Original author version and victor version server [voice_service.py](https://github.com/dyhhhhhh/chatgpt-web-voice/blob/9eb61526118d272beeb20ed18c0df071274d73e8/app/voice_service.py#L191) of `create_voice_session`: `excluded=set()` for each new request; 401 before `mark_invalid` and replace with the next one; other non-2xx/non-SDP directly 502. `_build_session_json` also fixes `client_tools:[]`. There is no account remaining voice balance/reset query, trusted quota event ledger, cooldown or concurrent occupation lease.
The client [usage / failover](https://github.com/dyhhhhhh/chatgpt-web-voice/blob/9eb61526118d272beeb20ed18c0df071274d73e8/static/voice.html#L1196) will read the candidate fields such as hang_up, rate_limit_message, audio_s of `usage_update` and arrange for reconnection; these are parsing assumptions that have been implemented by the code, not the real upstream event fixtures obtained in this round. `runAccountFailover` closes old media, releases binding, clears session ID and reconnects; `startCall({failover:true})` clears conversation/parent IDs, which is worth learning from. However, every time [accounts.py#L59](https://github.com/dyhhhhhh/chatgpt-web-voice/blob/9eb61526118d272beeb20ed18c0df071274d73e8/app/accounts.py#L59) takes the first enabled account, the client does not cool down/exclude the depleted account icon; **the same depleted account may be re-selected when 401 is not encountered**. "Change to another pool account" in the README cannot be regarded as the acceptance conclusion.
This round is executed with real `AccountPool`, temporary files and two fake tokens: A is selected for fresh `pick()` twice in a row; B is selected after `mark_invalid(A)`. This result proves the first account selection behavior, but does not prove the actual upstream quota or call success. victor's [import code](https://github.com/victorli-cn/chatgpt-web-voice/blob/9916f10368038fcebf0d17d6b6653d96aae0fd1b/app/accounts.py#L114) and [4 tests](https://github.com/victorli-cn/chatgpt-web-voice/blob/9916f10368038fcebf0d17d6b6653d96aae0fd1b/tests/test_accounts.py) read/run; import JSON, atomic rename, not Space's encrypted SQLite management system.
Additional checks [sivaneh fork](https://github.com/sivaneh/chatgpt-web-voice/tree/fab99f96d3c544161e68e2164e6b210302ff6520): HEAD 2026-09-27 10:41:07Z, newer than Space, but the key diff is Chinese UI/status to English, time zone to Asia/Kolkata, upstream language header to en-US. `pool.go` / `service.go` does not have new quota/tool/final capabilities; the status string also involves old library compatibility checks. Therefore, replacement is not recommended just because the date is new.
Class A deployments still require HTTPS, browser microphone permissions, and upstream reachability; the Python version relies on FastAPI, uvicorn, curl_cffi, Pydantic, and Pillow, and the Go management/key/persistent session layer will be lost or redone during migration. A more reasonable increment is to transplant the actual valuable recovery triggers to the existing gateway/client, and at the same time complete the lease, error classification, account isolation and idempotent bridging according to 03, and **not promote the candidate fields to trusted limit facts**.

These tool callbacks must be connected to the **Cylo persistent task plane** and cannot directly hand over the Worker/Codex credentials to the speech model. The provider tool call first persists the command and then executes it, and reconnection/replay remains idempotent; tool cancellation does not mean that the external side effects have been cancelled. If the plug-in actually gives completed, it is only applicable to the corresponding protocol of the plug-in and cannot be used to modify private subtitles on web pages.

## 5. Conditional recommendation and next step
1. **Current needs take priority: keep Space and learn from the failover entry of the original author's version of Python. ** First use real desensitization events to verify voice quota, final, relay annotation and first answer control; then do lease/cooling/number change, new session/idempotent Super bridge. Class A swaps cannot cross the acceptance threshold of 03/06.
2. ** In the future, the server will need to master media and mobile SDK: compare LiveKit Agents first. ** The condition is that the user accepts the new media server/room path, explicitly selects the API provider business plan, or invests a separate adaptation POC for the upstream of the original web page. Continuous calls cannot be guaranteed in the background/lock screen of the mobile phone, and native audio sessions and real phone acceptance are required.
3. **Prioritize private upstream protocol experiments/minimum server-side audio bridge in the future: compare with Pipecat. ** SmallWebRTC + frame pipeline is easier to observe and implement the adapter; the condition is to accept the Python media stack and self-written WebRTC/DC provider. First use fixed protocol trace to prove compatibility, and then discuss replacement; existing realtime plug-ins are not considered to have been adapted.
TEN will only enter subsequent comparisons when Agora is explicitly selected and its license conditions meet the delivery form. It's not a top three recommendation this round because permissions and paths add constraints that Cylo doesn't currently need.

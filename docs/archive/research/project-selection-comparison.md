# Cylo Open-Source Project Selection Comparison

Research date: 2026-10-21. This document answers the question, “Are there better projects besides Space3044/chatgpt-web-voice and awslabs/cli-agent-orchestrator?” Candidate source versions, licenses, and details are in [08 Voice Project Alternatives](reports/08-voice-project-alternatives.md) and [09 Agent Orchestration Alternatives](reports/09-agent-orchestration-alternatives.md). This page preserves the candidate research from 2026-10-21 and updates the current decision based on the user's latest clarification. The historical comparison does not replace the [product requirements](product-requirements.md).

**Decision at the time: the user had explicitly adopted OrchestratorInc/agent-orchestrator (AO, Go), with AO + the existing CLIProxyAPI + Space + Cylo's persistent control plane as the implementation path, and Go preferred for Cylo's new server.** Space's Go gateway, ChatGPT web real-time upstream, and voice account pool remain in use. The voice Agent handles listening, speaking, follow-up questions, and communicating results; Super handles complex planning and cross-Worker coordination; Cylo manages tasks, authorization, memory, and long-running ordinary services. The comparison below retains historical evidence and is no longer a representation that the foundation remains undecided.

**First distinguish the names: `awslabs/cli-agent-orchestrator` (CAO) is Python/FastAPI; `OrchestratorInc/agent-orchestrator` (AO, formerly the Composio project) currently has a Go core daemon. They are different projects.** The Space gateway is Go, so the first combination is Python + Go and the second is Go + Go.

This round adjusted its weighting based on the user's latest input: **manual seamless takeover is optional**. First-release emphasis is on automatic Super/Worker operation, recovery, background tasks, artifacts, and cost. Codex CLI execution, stopping, viewing, and recoverable identity remain required; candidates no longer have to first prove seamless handback between any CLI and Cylo. Real-time two-way voice, the ChatGPT web upstream, and multi-account quota handling still need direct evaluation. Separate STT/TTS or a separately paid API does not count as equivalent support.

## 2. Reuse and Integration Boundaries for the Selected Space Project

**No source evidence was found for a better project that already solves both quota rotation and the Super bridge through a direct replacement.** The user had explicitly chosen to keep the Space gateway. Account pools, leases, quota state, and a stable business bridge remain integration work, as described in [03](reports/03-voice.md).

The closest related projects are the Python projects [dyhhhhhh/chatgpt-web-voice](https://github.com/dyhhhhhh/chatgpt-web-voice) and [victorli-cn/chatgpt-web-voice](https://github.com/victorli-cn/chatgpt-web-voice). They use real web `access_token` credentials and `realtime/wm`; they do not mistake the official API key for a web token. The client has code that triggers reconnects from usage, hangup, and network signals and clears old session identifiers, which is useful for a failure state machine.

However, “reconnect” is not the same as “switch accounts when quota is exhausted.” The backend mainly disables a token and retries on **401**; other unsuccessful responses, including 429, return an error. A new request starts with an empty exclusion set. The client only clears its binding and does not put an exhausted account into a durable cooldown or exclusion list. A focused test with two fake accounts confirmed that, without disabling the first account, a fresh pick can select it again. Preserving subtitle history also does not prove that the new upstream session receives old business context. These projects did not demonstrate the full stable-final → idempotent command → real tool receipt loop. **Some mechanisms are portable; this is not a reason to replace the Go gateway with a Python rewrite.**

The more recent commits in [sivaneh/chatgpt-web-voice](https://github.com/sivaneh/chatgpt-web-voice) primarily adjust the interface and language; update recency alone does not establish better quota scheduling. Specific upstream and fork SHAs, differences, and experiments are in 08.

The advantage of the alternative LiveKit/Pipecat route is clearer real-time event and function-result interfaces; that belongs to the historical alternatives research. There is no need to continue comparing it now that the user has chosen the web upstream. If the user later authorizes a change, they would need to accept another upstream or maintain a web adapter themselves. The latter still carries private-protocol, account-scheduling, and bridge research; changing frameworks does not mean those problems are solved.

## 3. Choosing Among CAO, AO, and Client Tools

**After adopting AO, implementation responsibilities are as follows.** AO handles Agent orchestration, code execution, Codex sessions, and development workflows. Cylo decides when to invoke Super or route directly to a Worker and retains business authority. Basic CLI execution and recovery, real stopping, permissions, and artifact preservation still require acceptance; manual seamless takeover can be deferred.

| Product requirement | Current fit and implementation responsibility |
|---|---|
| Super on demand / direct Worker / separate worktrees (§§6, 8) | AO provides orchestrator/worker and isolated workspaces. Cylo decides when to invoke Super and routes simple actions directly; not all requests must pass through Super. |
| Basic CLI identity/recovery, stop, and results (§§4, 5, 8) | AO has native ID/resume and host/reconcile; real stopping and artifact preservation still need acceptance. Fresh fallback, dangerous permissions, and cleanup still need constraints; overall business recovery is not yet proven. |
| Ordinary long-running services, memory, permissions, and migration (§§7, 9–11, 14–17) | Neither project replaces Cylo's control plane, OS supervisor, evidence/authorization, or recovery ledger. AO development-product features do not satisfy these requirements. |
| Real-time web voice and account pool (§§3, 12) | Space is selected and connects to Cylo through idempotent commands/events. Voice interaction and background-task lifecycle are separate; feature acceptance does not reopen provider selection. |

The next step is therefore to implement the AO adapter and one goal → Worker → artifact → recovery path, without parallel CAO adapter development or a dual-daemon comparison. Codex account pools and outbound proxying reuse the existing remote CLIProxyAPI (document alias `existing-cli-proxy`); it does not need another deployment. The proxy selects and rotates accounts for each Codex route, so AO does not need to schedule the same pool again. Space's voice pool is managed separately. The user reported that current Codex login and use can go through the proxy; this was not tested in this document and does not mean per-account login isolation was verified.

The AO execution host connects to the instance using a reachable `codex_route.api_endpoint` and a server-side `codex_route.api_key_secret_ref`; actual values remain in deployment configuration. CLIProxyAPI does not own the execution workspace or native history; `CODEX_HOME`, threads, processes, and files remain on the execution host for persistence and recovery.

Only one execution owner manages a given run. AO manages code execution and Codex sessions; Cylo manages user-facing business tasks, authorization, long-running ordinary services, memory, and voice-pool scheduling. AO's ordinary recovery can “fresh launch while preserving the workspace” when native history is missing. **Preserving files is not the same as resuming the same thread**; Cylo must show the recovery mode and context loss.

[Happy](https://github.com/slopus/happy) / Hapi are worth researching as mobile/remote clients. Current Happy Codex code does use `codex app-server`, thread resume, approvals, and interruption, so it is inaccurate to describe it as only a screenshot terminal or to apply its advertised local/remote switching for other Agents directly to Codex. These projects mainly improve access and interaction; they do not automatically replace Super/Worker scheduling, the task ledger, or background-service supervision. Source and Hapi boundaries are in 09.

OpenClaw should no longer be treated as an API chat shell based on older impressions: the version examined in this round has real subagent dispatch, persistent owner checks, worktree assignment/cleanup, and Codex native app-server recovery, making it worth comparing as a complete platform. The tradeoff is redrawing responsibilities between Cylo and its Gateway/session/memory; it is not just a provider to plug into CAO. OpenHands received only a discovery check this round, not a deep source review, so it is not among the recommended alternatives here.

Vibe Kanban is also a development tool with real orchestration: `orchestrator_mode_router` restricts workspace scope, and session tools can create/run Coding Agents while rejecting execution inside the orchestrator itself. It should not be categorized as just a UI. Its Rust/Axum/sqlx backend adds a maintenance stack, and subsequent Codex startup uses `thread_fork` rather than same-thread resume, so it ranks below this round's AO and full-platform OpenClaw paths.

## 4. Technology Stack: Maintenance Preference and Historical Combinations

The current choice was an AO Go daemon + Space Go gateway, with Go preferred for Cylo's new server to reduce server-side build, debugging, and maintenance costs. A shared language does not replace protocol, storage, and permission boundaries: services connect through APIs/events and do not directly share databases, account tables, or arbitrarily import upstream `internal` modules. The table preserves other historical combinations to explain selection rationale.

Node/plugin capabilities need separate validation at a pinned version. Pipecat and LiveKit can both use real-time audio models; sharing a Python stack does not mean the system must fall back to STT/TTS.

## 5. Single Implementation Path and Review Conditions

**Proceed with AO + the existing CLIProxyAPI + Space + a Go-preferred Cylo control plane.** First connect basic CLI execution/recovery, stopping, explicit permissions, and artifact preservation. In parallel, follow the selected voice path to complete stable submission, receipt playback, and recovery through a new media session after quota exhaustion. The foundation is selected, but unaccepted features must still be marked as gaps.

AO native recovery and independent hosts are reusable foundations that still need integration acceptance. Preserve AWS CAO, OpenClaw, LiveKit/Pipecat, and client-project evidence without adding parallel validation paths. [10](reports/10-cao-ao-comparative-poc.md) records the existing cleanup experiment and current AO implementation sequence.

Assess maintenance from actual commits, tests, and implementation, not from stars or the latest push alone. LiveKit, Pipecat, and AO fixed HEADs all had code commits dated 2026-10-21 in this round. This indicates active development and also means versions must be pinned with upgrade regression checks; it does not establish an SLA. Fixed versions, maintenance, and license information for OpenClaw, Vibe Kanban, and clients are in 09. Specific commits and differences for Space/Python forks are in 08; an existing “in-call failover” comment is not a substitute for quota testing.

This round did not use real accounts, conduct paid real calls, run a complete AO/CAO fleet, or test macOS/iOS devices. Structured completed events still need Cylo idempotency, revisions, authorization, and a ledger; an open-source framework does not automatically provide business-level exactly-once behavior. The decision at the time was to advance the AO single path against the requirements; whether the product satisfies them must be judged from acceptance evidence.

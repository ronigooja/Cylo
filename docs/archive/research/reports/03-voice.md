# Cylo real-time voice implementation plan: upstream gateway, account pool and Super bridge
Study date: 2026-10-21. This report fully reviews the [complete product requirements](../product-requirements.md), this repository’s overall plan, architecture report 04, and existing voice evidence. This report corrects the prior selection: **The implementation path is the ChatGPT Web real-time voice upstream gateway and multi-account pool from Space3044/chatgpt-web-voice, with end-to-end two-way real-time voice as the main line.** The account voice quota is limited, and account selection, session stickiness, and recovery after the quota is exhausted are necessary components. Standalone STT+TTS is not implemented as an alternative to this requirement.
This article only delivers research, design, and offline research scripts; it does not write product runtime, deploy gateways, import real accounts, or make real calls. In this article, "source code has been implemented", "recommended to be added" and "pending POC" are strictly distinguished. Use OpenAI Docs skills to check official information, but the official Realtime capabilities are only used for comparison and protocol selection, and are not automatically applicable to the ChatGPT web page private protocol.
**Latest decision: Space3044/chatgpt-web-voice has been selected; the decision to adopt it will no longer depend on the business-bridging experiment. Subsequent verification will close integration gaps and determine which capabilities can be delivered.** For the responsibilities, concurrency and recommended topology of the speech model and Super, see [12 Boundary between Speech Agent and Super](12-voice-super-boundary.md).

## 2. Precise media, signaling and credential paths
```text
客户端麦克风 ←→ WebRTC/SRTP ←→ ChatGPT Web 实时语音服务
客户端私有 DataChannel(oai-events, negotiated id=0) ←→ 同一上游会话
       │ SDP offer/answer、会话控制、字幕/业务事件转送
       ▼
Cylo HTTPS/BFF + VoiceSessionAdapter ←→ 内部Go网关 /v1/voice/sessions
       │                               │ 选号/解密access_token
       │                               └→ POST https://chatgpt.com/realtime/wm?dcid=0
       │                                  multipart(sdp, session JSON)
       └→ Cylo command/task/event → 必要时Super → Worker/Codex
任务真实回执 → adapter → 客户端 → 私有relay_message → 上游实时语音回复
```
Connection establishment sequence: The user logs in through Cylo and explicitly opens the microphone → the control plane allocates session/device ownership and account lease (new) → the browser retrieves the media, establishes PeerConnection and DataChannel → transfers the offer to the internal gateway via Cylo BFF → the gateway uses ChatGPT in the pool `access_token` to `realtime/wm` → verifies the SDP answer and returns → the browser sets the remote description, and the media is directly connected to the upstream. The gateway does not decode/store audio, and ordinary HTTP account proxy is not a WebRTC media proxy; UDP is restricted/TURN and NAT paths must be tested on a real network.
The three credentials cannot be mixed: **Cylo login credentials** authenticate users/devices; **Gateway downstream Bearer API key** authenticate Cylo backend (the source code owner is `api_key:<id>`, which is the gateway key, not the official temporary token); **ChatGPT Web access_token** is held by the gateway and used upstream. This path does not have a confirmed official Realtime ephemeral key issuance step, and "the gateway has issued an official temporary token" cannot be added out of thin air. The client only takes the short-term Cylo session authorization and SDP/non-secret handle; the long-term gateway key, Web token, and encryption master key do not enter the browser, Super/Worker context or logs.
If all Cylo users share a gateway key, the gateway only recognizes one owner: BFF must verify tenant/user/session ownership again; the team version prioritizes the isolation of owner/key and account pool authorization per workspace, and accounts cannot be borrowed across tenants without authorization. The token AES-GCM seal, key hash, and sensitive field desensitization mechanism in the pool are retained; the encryption master key is independent of DB backup management. Account import, replacement, start, stop, and deletion are all subject to management permissions and auditing. The default value of `history_and_training_disabled:false` in the upstream session table is a fact of the source code. The available privacy settings need to be truly verified and configured according to the user data policy. It cannot be claimed that the audio/context will never enter the upstream history.
## 3. Account management and quota: source code boundaries and necessary additions
The existing management API supports account-by-account import of `access_token`, email, proxy, status/disabled, token update, enable/disable, delete, and activity detection; legacy import is an explicit migration tool and is not equivalent to universal multi-platform OAuth. The account pool will not be automatically refreshed and must be re-imported/replaced when expired. The list is only for preview; `tokenutil/jwt.go` decodes the exp locally and does not verify the signature. **exp only displays clues, not identity verification, voice quota or reset time**.
| Signal | Real semantics of source code | Implementation strategy (new) |
|---|---|---|
| `settings/user` 200+JSON | token accepted; remaining voice minutes/numbers/reset fields are not parsed | `auth_health=alive`, `quota=unknown`, "Quota Sufficient" is not displayed |
| Account `available` /PoolStats | Not manually disabled and status is not disabled | Renamed/interpreted as "tryable", separate from verified quota |
| wm 401 | `MarkInvalid`; New sessions can try the next account, sticky sessions will report an error directly without switching silently | Reserved; Authentication failure single column, replace the credentials and try again |
| wm 429 or other non-2xx | Currently returns 502 uniformly; there is no 429 rotation/quota cooling; network errors are also returned immediately | Retain the original HTTP/error classification and security response header, distinguish rate limit, clear quota exhausted, challenge/blocking, and transient network |
| The quota is exhausted during the call | There is no verified quota event analysis/restoration state machine | Establish a whitelist mapping after catching the real desensitization event; unknown errors remain unknown, and you cannot assert that the quota is exhausted just by saying "quota" in the subtitles |
| quota reset/balance | The current source code has no query API, parsing, storage or refresher | Unknown remains null; does not compile "recovery at a certain time every day" based on experience or commit each account to a fixed minute |
It is recommended to add `voice_account_state(account_id, auth_health, quota_state, quota_remaining nullable, unit nullable, reset_at nullable, reset_source, observed_at, cooldown_until, last_error_kind, next_probe_at)`. `reset_at` only accepts responses/trusted protocol events that can explain the field semantics and are observed after the server sends a request to the correct upstream, and saves the source/time/desensitization evidence summary; client reports, model text, JWT exp, and administrator estimates cannot be upgraded to "known resets". HTTP Retry-After is only interpreted as the time allowed to retry. Unless explicitly stated by the upstream, it cannot be used as an account voice quota reset.
When there is no trusted reset, exponential backoff + jitter + limited half-open detection, the UI displays "Unknown limit/cool down until a certain time before trying again". After cooling down, it will only enter probing, and it will change to `usable_observed` when the connection is successfully established. It still does not claim that the remaining amount is known. When it is clearly exhausted and there is no reset source, it enters exhausted and performs low-frequency detection according to the strategy; the administrator can request detection, but cannot activate the manufacturing quota by clicking on it. If the whole pool is unavailable, wait/prompt to replenish the account, and do not poll infinitely; plain text is temporarily available, but it is not called real-time voice delivery.
### Concurrent lease and session account stickiness (new)
`Pick` Adding mutex only "selects once" serially and does not reserve concurrent slots; LRU is not equal to load/quota scheduling. Add transactional `voice_account_lease(account_id, cylo_voice_session_id, owner, device_id, epoch, expires_at, state)`, the candidate meets the requirements of account activation, owner access, no cooling, and slot availability; the initial POC can only have 1 pass per account, the real concurrency support is unknown, and the upstream hard upper limit cannot be claimed to be 1. Number selection + reservation of the same transaction, SDP failure release; retry exclusion set, maximum number of attempts, total time budget are bounded, epoch check prevents old requests from overwriting new session status.
After the connection is successful, bind the account and upstream conversation/parent/voice ID to `media_generation`, and the entire call will not rotate round by round. Heartbeat renewal, clear hang-up release; recovery window temporarily retained when disconnected. Reconnection with the same account will give priority to using the original ID, but the source code comments admit that the upstream may ignore the resume field, so "field sent" is not a true recovery of the context. When the gateway restarts, the active metadata mark is released and the memory binding disappears. You cannot rely on SQLite records to claim that the media is disconnected.
The expiration of the lease does not prove that the direct connection WebRTC has stopped; the client needs to turn off the confirmation and quarantine of track/PeerConnection, and the slot cannot be reused immediately. When a malicious client does not cooperate, the existing signaling gateway cannot forcibly cut off the established media; if reliable server termination/hard concurrency guarantee is required, the upstream termination interface needs to be verified, or a new WebRTC endpoint/media relay held by Cylo (not ordinary TURN forwarding can provide application session control). Even if relay is added, a protocol POC is required, and it is not claimed to have been implemented.
### Exhausted number switching and context recovery (new)
Instantaneous network errors for the same account will be subject to boundary renegotiation first; authentication failure/exhaustion of clear quota → mark old generation as invalid, stop old audio, close old media, freeze old account/enter cooling → allocate other available accounts, **establish new upstream session**. Clear all upstream conversation/parent/voice IDs of the old account, and never pass the A account thread ID to B; Cylo conversation/project/task IDs remain unchanged. There will be a connection gap when changing numbers, and seamless migration of audio streams is not guaranteed.
The recovery package comes from the Cylo persistence repository: most recently confirmed user text/revision, received command IDs, true task status, necessary project facts, and scoped summary; no automatic replay of submitted business commands. Restoring the context through the private relay in the next section requires POC verification; it is the text background of the new session, not the model KV, speech prosody or original ChatGPT historical migration. When there is no reliable injection path, "New voice session, background task has been retained" is clearly displayed, requiring a brief retelling if necessary, and cannot pretend to have been restored. Late subtitles, receipts, and audio from the old generation must not pollute the new session; client playback gates are controlled by generation.
## 4. How to connect the real-time speech model to Super/Worker
The upstream ChatGPT voice assistant itself has the ability to understand and respond autonomously, and is positioned as an **interactive agent/session portal** in Cylo; VoiceSessionAdapter is a new deterministic protocol adaptation code in Cylo, and the two cannot be mixed into one component. The voice agent is responsible for real-time listening, speaking, clarification, and natural conversation, and only proposes business intentions. It does not own Cylo task status, authorization or Worker scheduling rights. Super is responsible for the formal planning and scheduling of complex tasks. Complex business requests are handed over to Super, and simple real status reading is performed with deterministic services; Worker executes independently according to the existing control plane authorization. The upstream voice model says "completed" without changing the task status. The screen receipt and task ledger are subject to the execution evidence.
### Source code capability matrix: Don’t mix protocols
| Capabilities | This repository/ChatGPT private path | Official Realtime comparison (another protocol/credential) |
|---|---|---|
| tools/function calling | `buildSessionJSON` explicit `client_tools:[]`, no Cylo tool schema, function call distribution/result return implementation | Official support for tools/function calling; official API session and server authorization required, schema cannot be directly inserted into the Web private interface and declared available |
| instructions | There are no special instructions to pass parameters or update the session; `primary_assistant` upstream identity exists | Official `session.update` and other instructions can be updated; no proof of Web acceptance |
| Inject text/context | There is already `relay_message` double-layer encapsulation + `buildBaseUserMessage(content_type:text,parts)`, the source role is user; the bottom layer is packaged again `data_message` + JSON string | Official `conversation.item.create` and function_call_output semantics cannot be transplanted to private payload |
| Subtitles | `chat_message_delta` full/append; compatible with transcript branches only "if any" | The official delta/completed boundary does not mean that private subtitles have the same final semantics |
| sideband | The gateway only acts as an agent for SDP, and no official call_id or server attach/WS entry was found | The official WebRTC call_id can be attached; the vs_/uppercase UUID on the Web side is not the call_id |
| Model | requested_default_model/model_slug is empty and is allocated by the upstream; voice_mode=wingman | The official model capability/price cannot be applied to this account to actually be assigned a voice model |
### Main line minimum bridge: subtitle/relay adapter (recommendation, real ability to be POC)
1. The client receives private subtitles and maintains partial/revision according to the provider message ID; forwards the security projection of the original protocol event to Cylo authenticated WSS/HTTP. The server assigns a stable ID to the turn. **The existing `rememberDcText` will save the changing text and cannot be directly used as the final task entry**. First, capture the real events to find reproducible turn completion signals, revisions and reordering rules; silence timeout alone cannot prove that the transfer is final. When no credible final is found, the POC explicitly presses the button to confirm/submit the sentence, which does not pretend to be complete without hands.
2. Complete user turn→persistence `voice.turn.committed`→idempotent command submission→server returns durable ack. Idempotent keys include Cylo conversation/turn/revision; revision is associated with the original command for correction strategy, and repeated business actions cannot be initiated. If the turn is not submitted and disconnected, the draft will remain; if the turn is submitted but the ACK is lost, the command status will be queried and will not be re-executed.
3. The adapter constructs the control plane `accepted/running/waiting/completed/failed` real receipt into a restricted text message, with `receipt_id/task_id/revision/generation` and trusted display original text; through the existing private `relay_message`, it requests the upstream voice assistant to explain the result with **user role text**. It is the smallest possible voice feedback path to try and cannot lie about supporting the system/tool ​​role. The synthesized receipt message ID must be included in the exclusion set, and its subtitles cannot be recognized as user service instructions again to form a loop.
4. The same real-time speech model continues to listen and accept interruptions. Receipt reporting relies on the current Web voice session and does not require independent TTS. It may rewrite, answer in advance, ignore the prompt or repeat the sound; the POC needs to verify when the upstream automatically answers, whether it can stop the current sound, press the receipt to trigger the voice, and whether the negative words/numbers are correct. Prompt word constraints are not security boundaries, and the control plane rejects any unauthorized business side effects; major approvals are bound to specific screen objects/command summaries.
5. **Answering the question twice requires explicit acceptance**: The upstream may respond to the user on its own first, and then broadcast the Cylo results later. The minimal version can clearly say "received/to be verified" first, but the source code does not yet have an interface that guarantees automatic reply suppression/customized identity. If it cannot be constrained, it will be recorded as a response/playback control integration gap and continue to be repaired in the selected upstream; at this time, only "real-time voice dialogue + Cylo independent task status" can be marked, the business voice closed loop has not been accepted, and the native call available is not pretended to be "Cylo execution closed loop available".
Bridge interface suggestions: input `voice.turn.partial/committed/interrupted`, `voice.session.error`; output `business.receipt.available`, `voice.context.bootstrap`, `voice.playback.stop`; public field `workspace_id/user_id/device_id/cylo_conversation_id/cylo_voice_session_id/media_generation/turn_id/provider_message_id/revision/event_id`. `business.receipt` contains real status/evidence references, and the sound is not authorized. The server treats client events as input provided by the user, and client forwarding cannot be used as upstream signature proof; forwarding of forged "task completed" changes to authoritative data is not allowed.
### Further protocol path (the same main line of requirements remains unchanged)
**Preferred enhanced POC:** Explore the actual schema, tool request/completion events, instructions/context roles and auto-reply switches of the Web private `client_tools` in the independent fork experimental branch. Obtain actual redacted request/response evidence and verify rejection/error behavior and side-effect boundaries item by item; field names or official examples alone do not prove support. If a private tool interface is found, bind a small set of `cylo_submit_request/cylo_get_task_status` tools, while execution remains in the control plane; never expose Worker credentials directly to the upstream.
**When direct server-side observation is needed:** explore whether the private upstream has a real sideband; there is currently no evidence of one. It can be changed to the Cylo backend as the upstream WebRTC peer and bridges the media/DataChannel to the client, so that business control does not rely on the front-end online, but it will add media operation and maintenance/delay/audio processing, which is a larger transformation POC, and cannot rely on media takeover to create non-existent tools/instructions capabilities.
**Protocol alternatives for comparison:** The official Realtime WebRTC+server sideband has documented tools/context control and can implement the same Cylo adapter contract, but uses official API credentials and independent billing, and does not use the Web token account voice quota.Enable this replacement provider only if the user selects it later; the current implementation retains the specified Web gateway/account pool, and this comparison must not replace the main path. The official Live and Realtime APIs appear on the same page; each protocol branch must still be pinned separately, and their events must not be mixed.

Goal (suggested, not achieved): Warm connection finished → first sound p50 ≤ 1.5 seconds, p95 ≤ 3 seconds (business Super reasoning single column); interrupt → speaker stops old sound p95 ≤ 350ms; 100 Chinese/number/negative/code name samples are sorted with semantic errors. Record speech_end, real final, durable_ack, Super result, upstream first tone, actual playback and interruption stop time; SDP success, subtitle update or network first byte cannot be regarded as aural delay.
Cost/limit observation: The remaining voice quota of the web account is not the API token price list. The observed success/failure/duration/switching times and sources are recorded by account; local call seconds cannot be used to deduce the actual remaining minutes or to ensure unlimited use of multiple accounts. Super/Worker fees, host bandwidth, and media relay (if used) are additional. What can be enforced is the number of sessions, concurrency, idle cutoff, and stop of new distribution in this system; the upstream quota cannot be increased by relying on the local ledger.
